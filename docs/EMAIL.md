# Письма: outbox, планировщик, диспетчер, Mailpit

Как рекомендации попадают в письмо-дайджест (SPEC F10, ADR-049, ADR-050). Почта только эмулируется: письма уходят
по SMTP в **Mailpit** (`http://localhost:8025`), наружу ничего не отправляется.

## Путь рекомендации до письма

1. **Outbox.** Правило открывает рекомендацию (в конце загрузки, по часовому таймеру воркера или при включении правила) —
   в той же транзакции `engine.notify_opened` пишет строку `email_outbox` со статусом `pending` и `created_at` из
   `Clock`. Откатилась транзакция — нет ни рекомендации, ни записи.
2. **План.** Диспетчер в воркере раз в 30 с (`DIGEST_TICK_S`) для каждого пользователя с ожидающими записями вызывает
   `planner.plan_send` (ADR-049) и сохраняет время и причину в запланированный дайджест — строку `email_digests` с
   `sent_at IS NULL` (у пользователя не больше одной, индекс `uq_email_digests_planned`).
3. **Отправка.** Когда `Clock.now() ≥ planned_at`, диспетчер в одной транзакции:
   - помечает `skipped` записи, чьи рекомендации уже закрыты (в письмо попадают только открытые);
   - если открытых не осталось — письма нет, запланированный дайджест удаляется, суточный лимит не расходуется;
   - иначе пишет письмо в строку дайджеста (`to_email`, `subject`, `body_text`, `body_html`, `sent_at`), привязывает к
     нему записи (`sent`, `digest_id`), проверяет индекс «один дайджест за местные сутки» (`flush`), отправляет письмо
     по SMTP и коммитит вместе с событием `digest.sent {id, local_date, count}`.
4. **Ошибка отправки.** Вся отправка ограничена таймаутом `SMTP_TIMEOUT_S` (10 с), поэтому зависший сервер не держит
   транзакцию и блокировку. При ошибке или таймауте транзакция отправки откатывается целиком: `sent_at` не ставится,
   записи остаются `pending`. Текст ошибки записывается в `email_digests.error` **отдельной короткой транзакцией** —
   строка запланированного дайджеста уже закоммичена на шаге «план», поэтому ошибка не пропадает вместе с откатом.
   Следующий тик повторяет отправку; успешная отправка очищает `error`.

## Когда уходит письмо (планировщик, ADR-049)

- Окно и потолок: 15 мин после последней рекомендации, но не позже 60 мин после первой (`DIGEST_WINDOW_MINUTES`,
  `DIGEST_MAX_DELAY_MINUTES`).
- Не больше одного письма за местные сутки (пояс из истории на момент отправки): иначе — 00:00 следующих суток.
- Тихие часы `[начало, конец)` переносят отправку на их конец; начало = конец — выключены. В ночь перевода часов назад
  конец тихих часов — первый момент после планового времени (второй проход повторённого часа, если нужно), вперёд —
  момент, когда часы перескакивают через конец (исправление шага 9.1, ADR-050).
- Причина переноса — `window`, `max_delay`, `daily_limit`, `quiet_hours`: видна в `GET /api/digests` и на dev-панели.
- Время отправленного дайджеста: `planned_at` — последний план до срока, `sent_at` — фактическая отправка (ближайший
  тик, то есть не позже чем через 30 с; после сдвига dev clock — тоже в пределах тика).

## Письмо

- Тема: «Трекер здоровья: N новых рекомендаций» с согласованием по числу — «1 новая рекомендация», «2 новые
  рекомендации», «5 новых рекомендаций» (отступление от буквального текста SPEC, согласовано, ADR-050).
- Тело — текст и HTML (`multipart/alternative`): список рекомендаций (название правила, дата, описание), ссылка
  `APP_URL/recommendations`, дисклеймер. Отправитель — `MAIL_FROM`.
- Адрес — `users.notify_email` (по умолчанию логин). Пусто — письма не планируются и не отправляются, записи ждут;
  `GET /api/digests` возвращает `warning: "no_notify_email"`. Предупреждение в интерфейсе — шаг 10.1.

## Защита от повторов

- `email_outbox.recommendation_id` уникален: одна запись на рекомендацию.
- `uq_email_digests_sent`: `UNIQUE(user_id, local_date) WHERE sent_at IS NOT NULL`.
- Диспетчер берёт пользователя под свою advisory-блокировку (`DIGEST_LOCK_NAMESPACE = 33`, не блокировку задач
  загрузки — длинная загрузка не задерживает письма); второй воркер пропускает занятого пользователя.
- Повторный тик после отправки ничего не находит: записей `pending` нет, запланированного дайджеста нет.
- Остаточный риск: если SMTP принял письмо, а коммит после него упал, следующий тик отправит письмо ещё раз
  (at-least-once в этом редком случае).

## Настройки (env)

| Переменная | По умолчанию | Что |
|---|---|---|
| `SMTP_HOST`, `SMTP_PORT` | `localhost`, `1025` (в compose — `mailpit`) | SMTP Mailpit, без TLS и логина |
| `SMTP_TIMEOUT_S` | `10` | потолок всей отправки письма |
| `MAIL_FROM` | `Трекер здоровья <noreply@health-tracker.local>` | отправитель |
| `APP_URL` | `http://localhost:5173` | ссылка в письме |
| `DIGEST_WINDOW_MINUTES`, `DIGEST_MAX_DELAY_MINUTES` | `15`, `60` | окно и потолок планировщика |
| `DIGEST_TICK_S` | `30` | тик диспетчера |

## Проверить руками

- Mailpit: `http://localhost:8025`; поиск писем через API — `GET /api/v1/search?query=to:"user@example.com"`.
- Очередь: dev-панель внизу страниц после входа или `GET /api/digests`; логи — `docker compose logs -f worker`
  (`digest_sent`, `digest_skipped`, `digest_send_failed`, `digest_tick`).
- Тест с настоящим Mailpit: `scripts/test.sh -m mailpit` / `scripts/test.ps1 -m mailpit` (скрипты сами поднимают
  postgres и mailpit).
