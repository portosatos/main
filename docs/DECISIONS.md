## ADR-001. Стек backend: Python 3.12 + FastAPI + SQLAlchemy 2.0 async + PostgreSQL
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §1.1, §5; Python, FastAPI и PostgreSQL утверждены заказчиком)
- **Контекст:** нужен отдельный backend на Python с PostgreSQL (§1.1 п. 2–3), массовая загрузка телеметрии,
  расчёт временных рядов, SSE, автоматическая документация API как доказательство работы.
- **Варианты:** (а) Django + DRF; (б) Flask; (в) FastAPI + SQLAlchemy 2.0 async + asyncpg + Alembic.
- **Выбор:** (в). Async-стек естественен для SSE и фонового воркера; Pydantic v2 валидирует вход;
  `/docs` (OpenAPI) — наглядная проверка API; SQLAlchemy Core и `COPY` дают быструю массовую вставку;
  Alembic — стандарт миграций и место для `CREATE EXTENSION btree_gist`. Пароли — argon2-cffi (argon2id),
  пояса — zoneinfo + tzdata, логи — structlog, пакеты — uv, тесты — pytest + hypothesis на настоящем Postgres.
- **Последствия:** весь backend async; интеграционные тесты требуют поднятого Postgres (тестовая БД).

## ADR-003. Очередь задач в PostgreSQL вместо Redis/Celery
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §5, §6.1, §7.1)
- **Контекст:** загрузка, пересчёты, правила и письма выполняются в фоне. Нужна надёжность: постановка задачи
  атомарна с изменением данных, задачи не теряются при падении воркера.
- **Варианты:** (а) Celery + Redis; (б) RQ/arq + Redis; (в) своя очередь `jobs` в Postgres:
  `FOR UPDATE SKIP LOCKED`, пробуждение через `LISTEN/NOTIFY`, возврат зависших задач по `locked_at` > 5 мин.
- **Выбор:** (в). Меньше сервисов, постановка в очередь в той же транзакции, проще локальный запуск на Windows.
  Последовательность задач одного пользователя — advisory lock по `user_id`.
- **Последствия:** свой код очереди и тесты на него (возобновление, зависшие задачи, параллельность пользователей).

## ADR-004. SSE для событий в реальном времени
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §5, F12)
- **Контекст:** изменения (прогресс, сводки, цели, рекомендации, настройки) должны появляться во всех вкладках
  пользователя ≤ 2 с. Поток нужен только от сервера к клиенту.
- **Варианты:** (а) polling; (б) WebSocket; (в) SSE (sse-starlette) + Postgres `NOTIFY` в канал `user_events`,
  каждый процесс API делает `LISTEN`.
- **Выбор:** (в). Cookie-авторизация работает «из коробки», EventSource сам переподключается, события между
  воркером и API идут через ту же БД. Полезная нагрузка — идентификаторы и даты, ≤ 8 КБ (лимит NOTIFY).
- **Последствия:** в nginx `proxy_buffering off`; фронтенд по событию инвалидирует ключи TanStack Query и делает
  полный refetch после переподключения.

## ADR-005. Исходные записи — источник истины, минутные таблицы — производный кеш
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.1, F4.3)
- **Контекст:** интервалы шагов приходят с произвольными, в том числе невыровненными границами; данные нужно
  уметь пересчитать при смене правил, поясов и после ошибок.
- **Варианты:** (а) хранить только агрегаты; (б) раскладывать в минуты при приёме и выбрасывать исходное;
  (в) хранить исходные записи (`steps_raw` с exclusion constraint на `btree_gist`, `sleep_raw`, `hr_point`) и
  считать из них `steps_minute`, `sleep_minute`, `coverage_minute` пропорциональными вкладами.
- **Выбор:** (в). Ничего не теряется на невыровненных интервалах; производные пересобираются
  (`htadmin rebuild`), пересчёт идемпотентен («удалить диапазон и вставить расчёт»).
- **Последствия:** больше места в БД; property-тест «сумма минут = сумма исходных».

## ADR-006. Классификация входящих записей new / duplicate / conflict / invalid
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.2)
- **Контекст:** повторная и частично пересекающаяся загрузка не должна менять итоги, а отчёт должен объяснять,
  что произошло с каждой записью.
- **Варианты:** (а) upsert «последний побеждает»; (б) молча игнорировать совпадения; (в) staging-таблица,
  схлопывание дублей внутри пачки и ровно один класс на запись; при конфликте побеждает первая загруженная
  запись (допущение SPEC).
- **Выбор:** (в). Загрузка идемпотентна, конфликты видны в отчёте (первые 50 с номером строки и причиной).
- **Последствия:** счётчики `new/duplicate/conflict/invalid` в `ingest_jobs`; разбор конфликтов в UI — «потом».

## ADR-007. Объединение устройств по минутам: часы важнее телефона
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.4, утверждено заказчиком)
- **Контекст:** часы и телефон пишут одну и ту же прогулку; сумма даст двойной счёт, а «максимум за день» потеряет
  прогулки, записанные только одним устройством.
- **Варианты:** (а) сумма; (б) максимум по дню; (в) приоритет устройства на уровне дня; (г) приоритет на уровне
  минуты: если минута покрыта часами — значение часов (0, если шагов нет), иначе телефона.
- **Выбор:** (г). Значение каждой минуты взято ровно с одного устройства, функция возвращает и `source_device_id`
  для проверки инварианта. Среди устройств одного типа приоритет у зарегистрированного раньше (допущение).
- **Последствия:** дневной итог может законно превышать итог любого устройства по отдельности; описание в
  `docs/MERGE_RULES.md`, property-тест инварианта.

## ADR-008. Сон относится к дню пробуждения
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F5, утверждено заказчиком)
- **Контекст:** ночной сон пересекает полночь; нужно однозначно отнести его к одной локальной дате.
- **Варианты:** (а) к дню засыпания; (б) делить по полуночи; (в) к дню пробуждения (как Garmin).
- **Выбор:** (в). Сессия — подряд идущие минуты сна с разрывами ≤ 30 мин, длиной ≥ 30 мин; засчитывается в дату
  окончания; основная сессия — самая длинная. Валидность ночи (`night_valid`) не зависит от статуса дня.
- **Последствия:** цель по сну и R1/R5 считаются по дню пробуждения.

## ADR-009. История часовых поясов пользователя
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F5)
- **Контекст:** пользователь путешествует; смещения в данных могут не совпадать с тем, как он хочет видеть дни.
  В день переезда ничего не должно теряться и удваиваться.
- **Варианты:** (а) один текущий пояс; (б) пояс из смещений в данных; (в) история `user_timezones(tz, valid_from)`
  из настроек; локальная дата события — по поясу, действовавшему в момент события.
- **Выбор:** (в). Каждое событие относится ровно к одной дате; сутки могут длиться 21–27 часов или состоять из
  двух кусков. Локальные даты считает только `services/localtime.py`.
- **Последствия:** смена истории запускает фоновый пересчёт затронутых дат и правил; описание в `docs/TIMEZONES.md`.

## ADR-010. Планировщик дайджеста — чистая функция `plan_send_time`
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F10)
- **Контекст:** письма: окно 15 мин, потолок 60 мин, не больше одного дайджеста в локальные сутки, тихие часы
  через полночь, смена пояса. Комбинации легко сломать.
- **Варианты:** (а) логика внутри диспетчера с БД и SMTP; (б) cron в фиксированное время; (в) чистая функция
  `plan_send_time(pending, last_digest_local_date, tz_history, quiet_hours, now)` + outbox + диспетчер раз в 30 с.
- **Выбор:** (в). Функция тестируется исчерпывающе без БД и SMTP; защита от повторов —
  `UNIQUE(user_id, local_date) WHERE sent_at IS NOT NULL`; причина переноса сохраняется в `email_digests`.
- **Последствия:** лимит и тихие часы сильнее потолка; после сдвига в тихие часы лимит проверяется повторно.

## ADR-014. Тесты до кода через strict-xfail
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 4)
- **Контекст:** заказчик хочет видеть по истории, что тесты появились раньше кода. Но `CLAUDE.md` §3 запрещает
  коммит с красными тестами.
- **Варианты:** (а) тесты и код одним коммитом — порядок не виден; (б) коммит красных тестов — нарушает
  `CLAUDE.md`; (в) коммит тестов с маркером ожидаемого падения: pytest `xfail(strict=True)`, Vitest `test.fails`,
  Playwright `test.fail()`; маркеры снимаются в коммите `feat(...)`.
- **Выбор:** (в). Strict-xfail на прошедшем тесте — ошибка, поэтому забыть снять маркер нельзя.
  Ответ пользователя: «Да, удачное решение: в истории будет видно, что тесты появились раньше кода».
- **Последствия:** коммит `test(<scope>): … (red)` не считается красным; `check_process.py` требует коммит
  `test(...)` раньше первого `feat(...)` шага; в WORKLOG пишутся сводки `N xfailed` и `N passed`.

## ADR-025. Clock: асинхронный `now()`, кеш сдвига, миграции при старте api
- **Дата:** 2026-10-10T20:26:17+06:00
- **Контекст:** SPEC F0: всё «сейчас» backend берёт из `app.clock.Clock`; в dev сдвиг хранится в `dev_clock` и
  должен совпадать у api и воркера; в prod сдвиг игнорируется. SPEC §4: миграции применяются при старте api.
- **Варианты:** (1) синхронный `now()` и фоновое обновление сдвига в каждом процессе; (2) асинхронный `now()`,
  сдвиг читается из БД с коротким кешем; (3) сдвиг через переменную окружения (не меняется на лету — не подходит).
  Для миграций: при старте api (команда контейнера), отдельный сервис-миграция в compose, в lifespan FastAPI.
- **Выбор:** вариант 2. `await clock.now()` / `await clock.read()` → `ClockReading(system_now, offset_seconds, now)`
  из одного чтения системного времени. Сдвиг кешируется на `CLOCK_CACHE_TTL_S` = 1 с; API после
  `POST /api/dev/clock` сбрасывает свой кеш, воркер видит новое значение не позже TTL. Сдвиг применяется только
  при `APP_ENV=dev`, при `test` и `prod` таблица не читается. `|offset_seconds| ≤ 10 лет`, иначе 422.
  Ответ GET/POST: `{offset_seconds, system_now, now}`. `dev_clock` — одна строка (`CHECK id = 1`), запись через
  `INSERT … ON CONFLICT`, нет строки → сдвиг 0. Миграции: команда контейнера api
  `alembic upgrade head && exec uvicorn …`; воркер в compose ждёт `service_healthy` у api. Роутер `/api/dev`
  подключается только при `APP_ENV=dev`, поэтому вне dev он отвечает 404, а не 403.
  Допущения агента, приняты пользователем: «ок, решения принимаю».
- **Последствия:** вызовы «сейчас» в бизнес-логике асинхронные (`await clock.now()`); инвариант закреплён тестом
  `unit/test_invariants.py`. Тесты получают Clock с фиксированным `system_now` и фейковым чтением сдвига.
  Интеграционные тесты работают в транзакции с откатом (`create_sessionmaker(conn)` — коммиты становятся
  savepoint'ами); тест «воркер и api видят один сдвиг» коммитит по-настоящему и чистит `dev_clock` после себя.

## ADR-026. Авторизация: сессии, CSRF-middleware, сид демо-пользователя
- **Дата:** 2026-10-10T20:54:10+06:00
- **Контекст:** SPEC F1: регистрация, вход, выход, `me`; серверная сессия на 14 дней в cookie `ht_session`
  (HttpOnly, SameSite=Lax, Secure в prod); argon2id; `X-Requested-With: ht` на всех изменяющих запросах;
  демо-пользователь `demo@example.com` с паролем из `.env.example`. SPEC §4: сид применяется при старте api.
  Не определены: срок жизни (абсолютный или скользящий), коды ответов, умолчания тихих часов, как сид получает
  пароль и как Swagger проходит CSRF-проверку.
- **Варианты:** CSRF — зависимость на каждом роутере или ASGI-middleware до маршрутизации; сид — в lifespan
  FastAPI или отдельной командой перед uvicorn; срок сессии — скользящий или абсолютный.
- **Выбор:**
  - сессия — 14 дней от входа по `Clock`, без продления; `last_seen_at` обновляется не чаще раза в минуту;
    истёкшая сессия удаляется при первом обращении; в БД `sessions.id = sha256(token)` (hex);
  - регистрация → 201 и сразу вход; вход → 200; выход → 204 (без сессии тоже 204); `me` → `{id, email,
    notify_email}`; неверный пароль и неизвестный email дают одинаковый 401, неизвестный email тоже проходит
    проверку argon2 (по времени ответа не видно, зарегистрирован ли адрес);
  - пароль 8–128 символов; `timezone` при регистрации обязателен, проверяется по базе tzdata; `notify_email`
    = логин; тихие часы выключены, заполнены 22:00–08:00; `created_at` и `valid_from` берутся из `Clock`;
  - CSRF — ASGI-middleware на все методы, кроме GET/HEAD/OPTIONS, до маршрутизации: новые маршруты защищены
    без доработок, запрос без заголовка на несуществующий путь получает 403, а не 404;
  - `/docs` отдаёт Swagger UI с `requestInterceptor`, который добавляет заголовок, как frontend;
  - сид — `python -m app.seed` в команде контейнера api после `alembic upgrade head`; данные из
    `DEMO_USER_EMAIL`, `DEMO_USER_PASSWORD` (`demo12345`), `DEMO_USER_TIMEZONE` (`Europe/Moscow`); пустой
    пароль — сид пропускается; если пароль в env сменили, при следующем старте обновляется только хеш.
  Допущения агента, приняты пользователем: «ок, допущения принимаю».
- **Последствия:** клиенты (frontend на шаге 1.3, генератор в потоковом режиме, smoke) шлют
  `X-Requested-With: ht` на всех изменяющих запросах. Тестовый клиент `tests/integration/client.py` делает это
  по умолчанию (`csrf=False` — без заголовка). Для выхода с других устройств или по всем сессиям понадобится
  отдельный эндпоинт (не в MVP).

## ADR-027. Frontend: вход, защищённый layout, dev-панель
- **Дата:** 2026-10-10T21:17:52+06:00
- **Контекст:** SPEC F0, F1, §6.4: страницы входа и регистрации, защищённый layout с шапкой, dev-панель (время
  `Clock`, сдвиг, ссылка на Mailpit). Стек SPEC §5: React 18, React Router, TanStack Query, react-hook-form + zod.
  Не определены: поведение при 401, поля регистрации, вид меню, единицы сдвига и адрес Mailpit на панели.
- **Варианты:** React Router 8 или 7; редирект при 401 — `location.assign` или навигация роутером; dev-панель —
  отдельная страница или полоса в layout; сдвиг — в секундах, часах или кнопками.
- **Выбор:**
  - `react-router` 7.x: 8.x требует React 19, а SPEC фиксирует React 18. `RouterProvider` берётся из
    `react-router` (вариант из `react-router/dom` в Vitest грузит вторую копию контекста роутера);
  - shadcn `Input` переписан на `forwardRef`: shadcn v4 генерирует компоненты под React 19 (`ref` — обычный
    prop), в React 18 `ref` терялся и react-hook-form не видел значений полей. То же нужно для будущих
    компонентов, в которые передаётся `ref`;
  - API-клиент: `credentials: "include"`, `X-Requested-With: ht` на всех методах, кроме GET/HEAD/OPTIONS; при
    401 вне `/api/auth/*` — навигация роутером на `/login` и очистка кеша запросов; 401 от `/api/auth/*`
    обрабатывают форма (неверный пароль) и `ProtectedRoute` (`/me`). После входа — возврат на запрошенную
    страницу или `/`. 4xx не повторяются, сеть и 5xx — до двух повторов;
  - регистрация: email и пароль (8–128), пояс браузера из `Intl…timeZone`, сразу вход; сообщения сервера
    показываются как есть (они на русском);
  - layout: шапка с email и «Выйти», пункты меню SPEC §6.4 с заглушками «Раздел появится на следующих шагах»;
    неизвестный путь → `/`; при выходе сначала уход на `/login`, затем очистка кеша (иначе закрытые страницы
    успели бы перезапросить данные);
  - dev-панель — полоса внизу layout (только после входа), скрыта, если `/api/dev/clock` → 404. Время `Clock`
    в поясе браузера, ru-RU, тикает раз в секунду между запросами (опрос раз в минуту); поле «Сдвиг, ч»
    (дробные, отрицательные) и кнопки «+1 ч», «+1 д», «Сброс»; после сдвига перезапрашиваются все остальные
    запросы: они зависят от «сейчас». Ссылка на Mailpit — `VITE_MAILPIT_URL` или тот же хост, порт 8025;
  - Vitest запускается с `TZ=UTC`, чтобы показанное время в тестах совпадало на любой машине и в CI.
  Допущения агента, приняты пользователем: «ок, допущения принимаю».
- **Последствия:** сдвиг больше чем на 14 дней завершает сессию (срок жизни по `Clock`, ADR-026) — после него
  нужно войти заново, это ожидаемо. Новые страницы добавляются в `src/lib/sections.ts` и `src/routes.tsx`.
  Тесты страниц рендерят маршруты через `src/test/render.tsx` (memory router и свежий кеш без повторов).

## ADR-028. Генератор `htgen`: пакет, период, модели устройств, детерминизм
- **Дата:** 2026-10-10T22:43:17+06:00
- **Контекст:** SPEC F13, §7.2, шаг 2.1 плана: детерминированный CLI `htgen` в `generator/` со своим `pyproject`.
  Не определены: значения по умолчанию для периода, seed и пояса, точные модели часов и телефона, суточный
  профиль, способ обеспечить одинаковые записи в пересечении периодов (нужно для шага 2.2).
- **Варианты:** CLI на argparse или click/typer; один генератор случайных чисел на весь запуск или отдельный
  на каждую дату; единица генерации — календарные сутки или «от отбоя до отбоя»; сон одной записью или
  с разрезом в полночь; сравнение доли шагов телефона по черному ящику или через внутренний API.
- **Выбор:**
  - пакет `htgen` (hatchling, src-layout), `[project.scripts] htgen`, argparse, из зависимостей только `tzdata`
    (на Windows у `zoneinfo` нет системной базы поясов); dev — pytest и hypothesis. Тесты генератора идут
    в `scripts/test.*` и в отдельной задаче CI `generator`;
  - период — локальные даты включительно; можно задать любые две из `--start/--end/--days`; только `--days` →
    период заканчивается вчера; одна граница или ничего → 7 дней; три опции сразу или `--end` раньше `--start` →
    exit 2. Пояс по умолчанию `Europe/Moscow` (`--tz` — шаг 2.2). `--seed` по умолчанию 0;
  - случайные значения даты D — из `random.Random("htgen:{seed}:{D}:{назначение}")` (seed-строка стабильна между
    платформами и версиями Python). Дата владеет окном `[D 00:00, D+1 00:00)` местного времени; параметры
    ночи берутся из seed даты подъёма, поэтому вечер D и утро D+1 согласованы без общей случайной
    последовательности. Сон через полночь пишется двумя соседними интервалами;
  - `--devices watch,phone` (по умолчанию оба). Часы: шаги на каждую минуту бодрствования (с нулями), пульс
    круглые сутки каждые `--hr-interval` с, сон с отбоем 22:30–00:30 на 6,5–8,5 ч. Телефон: интервалы по 5 мин
    в бодрствовании, 90–97% шагов часов на прогулке (доля задаётся на прогулку из 0,91–0,96), 40–80% вне
    прогулок, сон ±20 мин. Профиль: 1–3 прогулки, 2–3 сидячих периода, лёгкая активность;
  - `--unaligned` — сдвиг сетки шагов на 1–59 с на дату, одинаковый для обоих устройств;
  - вывод — UTF-8, только LF, компактный JSON; stdout по умолчанию; закрытый читателем stdout (`| head`) → exit 0.
  Допущения агента, приняты пользователем: «ок, допущения принимаю».
- **Последствия:** ночь, которая начинается до периода, обрезается в 00:00 первого дня, поэтому первая ночь периода
  обычно неполная. На шаге 2.2 пропуски и смена пояса ложатся на ту же схему «запись принадлежит своей дате».
  Пересечение периодов с одним seed даёт одинаковые записи по построению. Тесты определяют прогулки по выводу
  (минуты с ≥ 80 шагов): лёгкая активность в модели — не больше 40 шагов в минуту.

## ADR-029. Генератор: часовые пояса, пропуски, сценарии
- **Дата:** 2026-10-10T23:20:02+06:00
- **Контекст:** SPEC F13, шаг 2.2 плана: `--tz`, `--tz-change`, `--gap`, `--gap-prob`, `--gap-max-hours`,
  `--scenario`. Не определены: как устроены сутки при смене пояса, как читать время пропуска без смещения,
  как случайные пропуски сочетаются с детерминизмом по дате (ADR-028) и пересечением периодов, к каким датам
  привязаны сценарии.
- **Варианты:** сутки по стенным часам первого пояса или окно «от первого момента даты до первого момента
  следующей»; пропуски на весь запуск из одного генератора или по датам с просмотром назад; пропуск отбрасывает
  записи целиком или обрезает их; сценарии от конца периода или по абсолютным датам; один сценарий или несколько.
- **Выбор:**
  - история поясов `Timeline`: `--tz` (по умолчанию `Europe/Moscow`) и повторяемый `--tz-change МОМЕНТ=ПОЯС`
    (момент со смещением). Смещение каждой метки — по поясу в этот момент. Окно даты — от первого момента этой
    местной даты до первого момента следующей, поэтому день переезда длится не 24 ч (Москва → Нью-Йорк — 31 ч).
    Время суток в профиле отсчитывается от начала окна; перекрывшиеся ночи короткого дня пишутся одним сном;
  - `--gap ОТ/ДО[@watch|@phone]`: время без смещения — местное по истории поясов, без `@` — все устройства,
    можно повторять. В пропуске устройство не пишет ничего: сон обрезается, шаги продолжаются с конца пропуска,
    точки пульса пропускаются;
  - случайные пропуски: в дату D у устройства с вероятностью `--gap-prob` начинается пропуск от 1 ч до
    `--gap-max-hours` (по умолчанию 30, как в примере SPEC) из `Random("htgen:{seed}:{D}:gap:{устройство}")`.
    Пропуск отменяется, если в него (с запасом 1 ч) заходит пропуск, выпавший в предыдущую дату: решение
    зависит только от выпавших, а не от принятых пропусков, поэтому просмотр назад ограничен. Дата учитывает
    пропуски предыдущих дат, даже до периода, и пересечение периодов с одним seed совпадает;
  - сценарии отсчитываются от конца периода (файл до вчера → правило срабатывает на ближайшей оценке), берут
    значения из своих генераторов (`scenario:night`, `scenario:activity`, `scenario:hr`), сочетаются;
    `recovery` — только отдельно; минимальная длина периода у каждого сценария, иначе exit 2. Параметры —
    в `docs/DATA_FORMAT.md` и `generator/src/htgen/scenarios.py`;
  - без новых опций файл побайтно тот же, что на шаге 2.1 (тест с хешем).
  Допущения агента, приняты пользователем: «ок, допущения 1–5 принимаю».
- **Последствия:** записи в пересечении периодов совпадают без сценариев или при общем конце периода; со сценарием
  и разными концами отличаются последние дни. Генератор относит записи к датам по своему окну, а backend — по
  истории поясов из настроек пользователя (SPEC F5): после `--tz-change` нужно сменить пояс и в настройках
  (шаг 10.1), иначе дни будут посчитаны в старом поясе. Пропуски на краю ночи делают её невалидной
  (SPEC F6) — это и нужно для проверки критерия §9 #9.

## ADR-030. Приём данных: парсер, устройства, классификация
- **Дата:** 2026-10-10T23:46:05+06:00
- **Контекст:** SPEC F3, F4.1, F4.2, §7.2, шаг 3.1 плана. Не определены: обработка `\r\n`, пустых строк и BOM;
  предел длины строки (память не должна зависеть от размера файла); когда создаются устройства из `meta` (при
  возобновлении с контрольной точки на шаге 3.2 строка `meta` уже прочитана); как решать пересечения шагов внутри
  одного файла; где хранить ошибки; что делать с лишними полями и значениями, которые не помещаются в столбцы.
- **Варианты:** классификация целиком в SQL (оконные функции; для цепочки пересечений A–B–C «первая побеждает»
  в SQL не выражается без рекурсии) или SQL для сравнения с сохранёнными + проход по строкам пачки в Python;
  устройства из `meta` — при первой записи или при чтении `meta`; `INSERT … WHERE line = ANY(массив)` или соединение
  с `unnest(массив)`.
- **Выбор:**
  - парсер читает файл через `readline` с пределом 1 МиБ: длинная строка → `invalid`, её остаток пропускается
    по частям. `\r\n` принимается, пустые строки пропускаются (номер строки растёт), BOM в начале файла
    игнорируется, лишние поля игнорируются. `count` ≤ 2 147 483 647 (столбец `int`), строки без NUL и
    в UTF-8 — иначе `invalid`. У каждой строки номер и смещения начала и конца в байтах;
  - устройства из `meta` создаются при чтении `meta` (`INSERT … ON CONFLICT DO NOTHING`); существующие не меняются;
    неизвестное устройство → `phone`, имя = `id`, предупреждение — только при создании. Перед обработкой `meta`
    накопленная пачка записывается, поэтому результат не зависит от размера пачки;
  - пачка (5000) копируется `COPY` во временные staging-таблицы (`ON COMMIT DROP`), один SQL-запрос на тип даёт
    вердикт против сохранённых (`duplicate`, другое значение, пересечение шагов через GiST-индекс exclusion
    constraint). Затем записи пачки, которым ничего не помешало, сравниваются между собой в порядке строк:
    повтор ключа → `duplicate` или `conflict`, пересечение шагов с принятым интервалом → `conflict`. Принятые
    вставляются соединением с `unnest` (с `= ANY` пачка шла в 1,5 раза медленнее);
  - `Counts` хранит не больше 50 ошибок, счётчики считают все; `ingest_records` не делает commit — пачки
    и контрольные точки коммитит воркер (шаг 3.2);
  - минимальная `ingest_jobs`: столбцы §7.1 без `file_path`, `bytes_total`, `bytes_done` (шаг 3.2).
  Допущения агента, приняты пользователем: «ок, допущения 1–7 принимаю».
- **Последствия:** неделя htgen (129 тыс. записей) принимается примерно за 10,6 с, повтор (всё `duplicate`) —
  за 4,6 с (замер на ноутбуке разработки). Целевые 3 млн записей за ≤ 5 мин (SPEC §4) проверяются на шаге 13.1.
  Если файл с `meta` не в первой строке, устройства, встреченные до неё, станут телефонами.

## ADR-031. Очередь задач, воркер и загрузка файла
- **Дата:** 2026-10-11T00:24:38+06:00
- **Контекст:** SPEC F3, §4, §6.1, §7.1, шаг 3.2 плана. Не определены: как один пользователь получает строго
  последовательную обработку при нескольких воркерах; где граница контрольной точки и что значит «продолжить
  со смещения»; как длинная задача отличается от зависшей; что делать при ошибке обработчика; где хранить тик
  воркера и влияет ли он на `/api/health`; как принять файл 500 МБ, не держа его в памяти и не копируя дважды.
- **Варианты:** выбор задачи с `NOT EXISTS (running того же пользователя)` (гонка между воркерами) или
  `SKIP LOCKED` + advisory lock на пользователя; контрольная точка отдельно от записей (повтор даёт `duplicate`)
  или в той же транзакции; `UploadFile` Starlette (весь файл сначала во временный файл, потом копия в volume) или
  потоковый разбор multipart.
- **Выбор:**
  - `jobs` — очередь в той же БД; порядок по `id` (identity), а не по `created_at`: время `Clock` в dev сдвигается.
    Захват — `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED LIMIT 1)`, затем `pg_try_advisory_lock(32,
    hashtext(user_id))` на отдельном соединении воркера (сессионный, держится всю задачу). Занят — захват
    откатывается, пользователь пропускается. Падение процесса закрывает соединение и снимает lock;
  - `enqueue` делает `pg_notify('jobs')` в транзакции постановки, воркер слушает `LISTEN jobs` и раз в
    `WORKER_TICK_S` (30 с) делает тик: heartbeat в `worker_heartbeat` и возврат задач с `locked_at` старше 5 мин
    по `Clock`. После каждой пачки обновляются `locked_at` задачи и heartbeat — длинный файл не считается
    зависшим;
  - `ingest_file`: пачка — 5000 строк файла; записи, счётчики, ошибки (первые 50 по номеру строки),
    предупреждения и контрольная точка (`bytes_done`, `lines_done`) — одна транзакция. Возобновление —
    `parse_lines` с `start_offset`/`first_line`, результат равен прогону без перерыва (поэтому «уже вставленные
    записи станут `duplicate`» из SPEC F3 у нас не возникает). SIGTERM: воркер дописывает текущую пачку и сразу
    возвращает задачу в очередь;
  - ошибка обработчика → `jobs.failed` (`last_error`) и `ingest_jobs.failed`, без повторов; файл остаётся.
    После `done` файл удаляется;
  - `/api/health` → `worker: {status: ok|stale|unknown, last_tick_at}`, `stale` — тик старше 120 с; код ответа
    от воркера не зависит (healthcheck api в compose, а воркер стартует после healthy api);
  - `POST /api/ingest/files` разбирает multipart потоково (`python-multipart`) и пишет часть `file` прямо в
    `/data/ingest/<user_id>/<job_id>.ndjson`; лимит — сразу по `Content-Length` и по фактическим байтам → `413`.
    Регистрация `ingest_jobs` и постановка в очередь — одна транзакция. nginx: `client_max_body_size 501m`;
  - тесты очереди коммитят в тестовую БД по-настоящему (разные соединения), пользователи `@jobs.example.com`
    удаляются фикстурой.
  Допущения агента, приняты пользователем: «ок, допущения 1–13 принимаю».
- **Последствия:** замер на ноутбуке разработки (стек в Docker Desktop): htgen 30 дней (554 тыс. записей,
  43 МБ) — 32 с, повтор — 20 с (всё `duplicate`); 90 дней (1,66 млн записей, 129 МБ) — 94 с, около 17,7 тыс.
  записей/с, память воркера около 60 МБ. Оценка для 3 млн записей из SPEC §4 — около 3 мин только на приём; минутные
  таблицы (шаг 3.3) добавят своё время, итог проверяется на шаге 13.1. Один воркер обрабатывает одну задачу за раз;
  параллельность разных пользователей требует нескольких процессов воркера.

## ADR-032. Минутные таблицы: пересчёт после пачки и пересборка
- **Дата:** 2026-10-11T01:03:09+06:00
- **Контекст:** SPEC F3 (производные данные обновляются по ходу обработки), F4.3, §4 (пересчёт только затронутых
  диапазонов, `htadmin rebuild --user`, пересборка даёт тот же результат), шаг 3.3 плана. Не определены: когда и в
  какой транзакции пересчитывать, как выбирать диапазоны, в каком типе суммировать вклады шагов, что делает
  пересборка, если в этот момент у пользователя идёт загрузка, как вызвать `htadmin` в контейнере.
- **Варианты:** пересчёт отдельной задачей `recompute` в очереди (минуты отстают от исходных записей, нужна склейка
  задач) или в транзакции пачки; один общий диапазон на устройство за пачку (при разбросанных записях пересчитывается
  лишнее) или объединённые диапазоны задетых минут; сумма в `double precision` (результат зависит от порядка
  сложения, пересборка может отличаться в последнем бите) или в `numeric`.
- **Выбор:**
  - после каждой пачки `ingest_records` пересчитывает минуты, задетые её **новыми** записями, в той же транзакции,
    что записи и контрольная точка: после падения воркера минуты не расходятся с исходными записями, а пачка без
    `new` ничего не пересчитывает;
  - задетые минуты: интервал `[start, end)` → минуты от `floor(start)` до `ceil(end)`, точка пульса → её минута.
    Диапазоны устройства сливаются (пересекающиеся и соседние) и передаются тремя массивами; на каждую таблицу —
    `DELETE` диапазонов и один `INSERT … SELECT` (`services/minutes.py`);
  - `steps_minute`: сумма `count × секунды пересечения / длина интервала` в `numeric`, запись в `real` (SPEC):
    сумма точная, значение минуты не зависит от разбиения на пачки. Минуты с 0 шагов записываются;
  - `sleep_minute`: интервалы сна устройства, обрезанные диапазоном, объединяются (`range_agg`), минута отмечена,
    если объединение покрывает ≥ 30 с; поиск интервалов ограничен 24 ч назад (валидация §7.2);
  - `coverage_minute`: объединение минут интервалов шагов и сна и минут точек пульса;
  - `rebuild_user` берёт `pg_advisory_xact_lock` пользователя (тот же ключ, что у воркера): ждёт текущую задачу
    пользователя. Удаляет все производные строки устройств пользователя и считает их заново кусками по 7 дней;
  - `htadmin` — `app/cli.py` (argparse), в образе обёртка `/opt/venv/bin/htadmin` → `python -m app.cli`; email
    ищется без учёта регистра, неизвестный → exit 1.
  Допущения агента, приняты пользователем: «ок, допущения 1–6 принимаю».
- **Последствия:** замер (htgen 90 дней, 1,66 млн записей, 129 МБ, ноутбук разработки, Docker Desktop): приём с
  пересчётом минут — 85–86 с на прогретом стеке (127 с — первый прогон сразу после пересборки стека), без пересчёта в
  тех же условиях — 66 с, то есть пересчёт добавляет около 20 с (~30 %). Память воркера около 60 МБ. Повторная
  загрузка — 30 с, хеши минутных таблиц не меняются. `htadmin rebuild` для этого пользователя — 11,4 с,
  результат совпадает с инкрементальным. Оценка для 3 млн записей — около 2,5–4 мин, укладывается в 5 мин SPEC §4;
  окончательно — шаг 13.1.

## ADR-033. Локальные даты по истории поясов: `services/localtime.py`
- **Дата:** 2026-10-11T01:23:45+06:00 (шаг 4.1)
- **Контекст:** SPEC F5 и ADR-009 задают историю `user_timezones(tz, valid_from)` и правило «дата события — по поясу,
  действовавшему в момент события», шаг 4.1 плана. Не определены: какой пояс действует до первой записи (она
  создаётся при регистрации, а файлы содержат данные за прошлые месяцы), где начинаются сутки, если 00:00 в поясе
  нет из-за перевода часов, и читает ли модуль историю из БД сам.
- **Варианты:** до первой записи — отбрасывать данные, считать в UTC или в первом поясе; начало суток —
  `combine(day, 00:00)` «как получится» или явно первое мгновение даты; модуль с запросами к БД или чистые функции.
- **Выбор:**
  - `TzHistory(records)` — чистый класс над записями с полями `tz` и `valid_from` (строки `UserTimezone` подходят
    как есть); записи сортируются, пустая история и время без пояса → `ValueError`, неизвестный пояс →
    `ZoneInfoNotFoundError`. Методы: `zone_at(ts)`, `local_date(ts)`, `ranges_for_date(day)` — UTC-интервалы
    `[start, end)`, отсортированные, соседние куски склеены;
  - запись действует с `valid_from` включительно; **первый пояс действует и до своего `valid_from`** (данные до
    регистрации);
  - сутки в поясе — от первого мгновения даты до первого мгновения следующей: 00:00 с `fold=0`; если 00:00 попадает
    в «дыру» перевода часов (Сантьяго, 6 сентября 2026), сутки начинаются с её конца (01:00);
  - внутри одного пояса дата считается неубывающей: переводов часов назад через полночь (например, 00:30 → 23:30)
    в выбранных зонах нет; property-тесты гоняют пояса с переводом в полночь (Сантьяго, Гавана, Бейрут);
  - загрузчик истории из БД появится там, где он нужен (шаги 4.2–4.3).
  Допущения агента, приняты пользователем: «ок, допущения 1–3 принимаю».
- **Последствия:** в день переезда сутки длятся 17–31 ч или состоят из двух кусков, каждое мгновение относится ровно
  к одной дате (property-тест), сумма за период при смене пояса не меняется. Дни считаются по поясу из настроек, а
  `htgen` по умолчанию пишет `Europe/Moscow`: в демо-скрипте и e2e (шаги 12–13) генератор запускается с `--tz`
  пояса пользователя, иначе «сутки» данных и дни сводок разойдутся.

## ADR-034. Объединение устройств и метрики дня без сна: `merge.py`, `metrics.py`
- **Дата:** 2026-10-11T08:27:12+06:00 (шаг 4.2)
- **Контекст:** SPEC F4.4 и ADR-007 задают правило «часы важнее телефона» по минутам, F6 и F7 — время ношения,
  статус дня, шаги, активные минуты, пульс в покое (10-й перцентиль в минуты без шагов, ≥ 60 минут) и пик (максимум
  поминутных медиан). Не определены: порядок устройств, зарегистрированных в один момент (все устройства одной
  meta-строки получают одинаковый `created_at`); над чем считать перцентиль (точки или минуты) и каким методом; что
  такое «минута без шагов» при дробных вкладах; к какой дате относится минута на границе суток; шаги дня, где есть
  только пульс.
- **Варианты:** порядок при равенстве — случайный `id`, `external_id`, порядок в meta; перцентиль — по всем точкам
  или по минутным медианам, nearest-rank или линейная интерполяция; «без шагов» — `= 0` или `< 1`; шаги дня только с
  пульсом — `null` или 0; объединение в SQL или в Python.
- **Выбор:**
  - `merge.py` — чистые функции: `device_order` (часы → телефоны, затем `created_at`, затем `external_id`),
    `merge_steps` (источник — первое по приоритету устройство, **покрывающее** минуту; без шагов — 0),
    `merge_hr` (источник — первое по приоритету устройство **с пульсом** в минуте); результат —
    `{minute_utc: Merged(value, source_device_id)}`;
  - `metrics.py`: `day_metrics(session, user_id, day)` читает историю поясов (`localtime.load_tz_history`),
    устройства, `coverage_minute`, `steps_minute` и минутные медианы `hr_point` (`percentile_cont(0.5)` в SQL) за
    UTC-интервалы дня, объединяет в Python и считает чистой `summarize_day`;
  - минута относится к дате своего начала: границы дня округляются вверх до минуты;
  - пульс минуты — медиана её точек; пульс в покое — 10-й перцентиль минутных медиан с линейной интерполяцией
    (как `percentile_cont`) по минутам с объединённым значением **ровно 0**;
  - шаги дня — сумма объединённых минут, округлённая до целого; день только с пульсом — `partial`, шаги и активные
    минуты 0, а не `null`.
  Допущения 1–4 агента приняты пользователем: «ок, допущения 1–4 принимаю».
- **Последствия:** инвариант «одно устройство на минуту» проверяется property-тестом; день может законно превышать
  итог любого устройства (пример 5000 в `docs/MERGE_RULES.md`). Сон, `daily_summaries` и пересчёт «грязных» дат —
  шаг 4.3: там `summarize_day` дополнится сном, а `day_metrics` станет источником строки сводки.

## ADR-035. Уточнение SPEC F6: правило валидной ночи (`night_valid`)
- **Дата:** 2026-10-11T08:53:33+06:00 (шаг 4.3)
- **Контекст:** SPEC F6 (допущение) определял валидную ночь так: основная сессия существует, «в 60 минутах до её
  начала и в 60 минутах после конца есть данные», а внутри сессии нет пропусков данных длиннее 30 минут. Цель
  правила — снятые посреди ночи часы не должны превращаться в «короткий сон». При разборе тестов шага 4.3 выяснилось:
  - условие о внутреннем пропуске ничего не добавляет: сессия — это минуты сна с разрывами не больше 30 минут, а минута
    сна всегда покрыта данными, так что пропуск данных длиннее 30 минут внутри сессии невозможен — он её разрывает;
  - буквальное «есть данные» (хотя бы одна минута) не ловит главный случай: часы сняли на 31 минуту в 02:00, ночь
    делится на сессии 23:00–02:00 и 02:31–07:00, основная — вторая, в часе до неё есть данные (первая часть ночи),
    и ночь становится валидной с 4,5 ч сна вместо 7,5 ч.
- **Варианты:**
  1. буквальное прочтение (хотя бы одна минута данных в каждом часовом окне);
  2. каждое часовое окно покрыто полностью — слишком строго: часы, надетые за 10 минут до сна, делают ночь
     невалидной;
  3. в окне [начало − 60 мин, конец + 60 мин] нет пропуска данных длиннее 30 минут — тот же порог, что у разрыва
     сессии.
- **Выбор:** вариант 3, предложен агентом, утверждён пользователем («принимаю твоё правило: в окне [начало − 60 мин,
  конец + 60 мин] нет пропуска данных длиннее 30 минут»). Пропуск данных — подряд идущие минуты, которые не покрыло
  ни одно устройство (`coverage_minute`); у пропуска на краю окна считается только часть внутри окна. Окно считается
  по минутам: от минуты `начало − 60` до минуты `конец + 59` включительно, где `конец` — конец последней минуты сна.
  SPEC F6 исправлен.
- **Последствия:** часы, надетые не позже чем за 30 минут до сна и снятые не раньше чем через 30 минут после
  пробуждения, дают валидную ночь; снятые посреди ночи больше чем на 30 минут — невалидную, даже если снова надеты.
  Часы, снятые ночью, когда телефон продолжает записывать сон, ночь не портят: после объединения сон и покрытие идут от
  телефона (SPEC F4.4). Проверяется `unit/test_sleep.py` (9 случаев `night_valid`, «часы сняты посреди ночи»).

## ADR-036. Сон, `daily_summaries` и «грязные» даты при загрузке
- **Дата:** 2026-10-11T09:01:25+06:00 (шаг 4.3)
- **Контекст:** SPEC F3, F5–F7 и шаг 4.3 плана: сессии сна и день пробуждения, основная сессия, `night_valid`
  (ADR-035), таблица `daily_summaries`, пересчёт затронутых дат по ходу загрузки не реже раза в ~2 с, сводки в
  `htadmin rebuild`. Не определены: как мерить длину сессии, к какой дате относится сон, закончившийся ровно в 00:00,
  что хранить для дня без данных, какие даты считать «грязными» и где их держать между сбросами.
- **Варианты:** длина сессии — от начала до конца или только минуты сна; дата сессии — дата мгновения конца или
  последней минуты; грязные даты — только дата изменённой минуты, дата ± сутки или точный поиск по сессиям; хранение
  — в памяти воркера, отдельная таблица или колонка задачи; пересчёт — в каждой пачке или с интервалом.
- **Выбор:**
  - `services/sleep.py` — чистые функции. Сессия — объединённые минуты сна с разрывами ≤ 30 мин; длина — число минут
    сна (разрывы не входят), от 30 минут; дата — дата **последней минуты** сна; основная — самая длинная, при
    равенстве более поздняя; день без сессий — сон `null`, `night_valid = false`. Допущения 1–4 приняты
    пользователем: «ок, допущения 1–4 принимаю». `merge.merge_sleep` берёт источник минуты как для шагов;
  - `metrics.compute_day` читает покрытие и минуты сна за [начало дня − 48 ч, конец дня + 2 ч]: сессия длиннее
    48 ч была бы обрезана (реальные намного короче). `DayMetrics` дополнен полями сна;
  - `daily_summaries` (миграция 0006) — производная, как минутные таблицы: `recompute_dates` заменяет строки заданных
    дат, день `no_data` строки не имеет (удаляется), `computed_at` — от `Clock`; `rebuild_summaries` пересчитывает
    все даты от первой до последней покрытой минуты, `htadmin rebuild` делает это после минутных таблиц;
  - грязные даты пачки (`summaries.affected_dates`) — даты интервала [изменённые минуты − 91 мин, + 91 мин]
    (разрыв сессии 31 мин + окно валидности 60 мин) и дни пробуждения сессий, которые его задевают, с просмотром
    вперёд до 48 ч. Если в интервале нет ни одной минуты сна, сессии не ищутся. Для перечисления дат интервала при
    смене пояса добавлен `TzHistory.dates_between`;
  - даты копятся в `Counts.dirty_dates` и в задаче (`ingest_jobs.dirty_dates`), коммитятся вместе с контрольной
    точкой. Сводки пересчитываются в транзакции пачки: после первой пачки сразу, затем если с прошлого сброса прошло
    ≥ `summary_flush_s` (2 с, `time.monotonic`), остаток — в транзакции, завершающей задачу. Упавший воркер не
    теряет даты: продолженная задача досчитает их.
- **Последствия:** сводка появляется до `ingest.done` (§9 #7) и совпадает с полной пересборкой (тесты и живой стек:
  хеши `daily_summaries` равны). На живом стеке файл 55 тыс. записей (3 дня) — 5 с. Событие `summary.updated` с
  датами сброса — шаг 5.1; пересчёт дат при смене пояса — шаг 10.1 (`recompute_dates` уже принимает любой набор дат).

## ADR-037. Уточнение SPEC F7: разница по сну в дневной сводке — только между валидными ночами
- **Дата:** 2026-10-11T09:29:09+06:00 (шаг 4.4)
- **Контекст:** SPEC F7: дневная сводка показывает разницу с днём D−1, «если одной из сторон нет — нет данных для
  сравнения». Не сказано, сравнивать ли сон невалидной ночи (снятые посреди ночи часы дают «короткий сон», ADR-035) и
  значения дней `partial`. Недельное среднее сна по F7 считается только по валидным ночам.
- **Варианты:**
  1. сравнивать любые непустые значения всех метрик, статус и `night_valid` отдать интерфейсу (предложение агента);
  2. для сна — только если обе ночи валидны, остальные метрики — по любым непустым значениям;
  3. сравнивать только дни `complete` и валидные ночи.
- **Выбор:** вариант 2, решение пользователя: «для шагов, активности и пульса разница по любым непустым значениям
  (как ты предложил), а для сна — только если обе ночи валидны (night_valid = true с обеих сторон), иначе разница по
  сну null». Согласуется с недельным средним сна по валидным ночам. SPEC F7 дополнен.
- **Последствия:** `delta.sleep_minutes = null`, если у дня D или D−1 `night_valid = false`, хотя `sleep_minutes`
  обоих дней в ответе есть. Разница шагов дня `partial` считается, пометку «неполные данные» показывает интерфейс
  (статус в ответе). Проверяется `test_day_delta_null_when_previous_no_data`.

## ADR-038. API сводок: `/api/summary/day|week|range`
- **Дата:** 2026-10-11T09:32:12+06:00 (шаг 4.4)
- **Контекст:** SPEC F7 и §6.3, шаг 4.4 плана: дневная и недельная сводки со сравнением и базами усреднения, ряд по
  дням для графиков. Не определены формат ответа, округление, разница при нуле и при пропуске, формат и границы
  недели, предел диапазона, значения по умолчанию.
- **Варианты:** считать разницу в API или отдавать только значения (считает интерфейс); агрегаты недели в SQL или в
  Python по 14 дням; неделя — `YYYY-Www` или дата понедельника; параметры по умолчанию («сегодня» по `Clock` и поясу)
  или обязательные; диапазон без предела или с пределом.
- **Выбор** (допущения 1, 2, 4, 5, 6 агента приняты пользователем: «ок, допущения 1, 2, 4, 5, 6 принимаю»; пункт 3 —
  ADR-037):
  - разница считается в API (`services/weekly.py`): `{abs, pct}`, округление до 0,1 от показанных значений,
    `pct = null` при прошлом 0, `null` при пропуске с любой стороны;

  - `date`, `week`, `from`, `to` обязательны; `range` — обе границы включительно, ≤ 366 дней, иначе 422;

- **Последствия:** интерфейс (шаг 6.1) не повторяет правила F7 и показывает разницу как есть; «N из 7» —
  `metrics.<m>.days`. Описание — `docs/API.md`. Проверяется `integration/test_summary_api.py` (9 тестов).

## ADR-039. События: NOTIFY `user_events`, `EventHub` в API и поток `GET /api/events`
- **Дата:** 2026-10-11T10:08:45+06:00 (шаг 5.1)
- **Контекст:** SPEC F3 и F12, шаг 5.1 плана: события воркера должны доходить до всех вкладок пользователя за ≤ 2 с,
  прогресс загрузки — не реже раза в 2 с, полезная нагрузка — не больше 8 КБ (лимит NOTIFY). Не определены формат
  событий, поведение при обрыве LISTEN, событие о неудачной задаче, частота прогресса, момент, с которого поток
  гарантированно получает события.
- **Варианты:** соединение LISTEN на каждый поток SSE или одно на процесс; при обрыве LISTEN — закрыть потоки (вкладки
  переподключатся сами) или держать их и прислать событие «перезапроси всё»; прогресс после каждой пачки или с
  ограничением частоты; авторизация потока через общую зависимость (сессия БД живёт весь поток) или своей короткой
  сессией.
- **Выбор** (допущения 1–7 агента приняты пользователем: «ок, допущения 1–7 принимаю»):
  - `services/events.py`: `publish` — `pg_notify('user_events', {"user_id","type","data"})` в транзакции вызывающего,
    событие уходит при коммите (вкладка перезапрашивает уже записанное); больше 7900 байт → `ValueError`;
    `publish_summary_updated` делит отсортированные даты на части, каждая < 8000 байт;
  - `EventHub`: одно соединение asyncpg на процесс API (`application_name = ht-events`), запускается в lifespan в
    фоне (лежащая БД не мешает старту), переподключение с паузой 0,2 → 5 с, проверка `SELECT 1` раз в 5 с. После
    переподключения всем потокам — `resync` (события за время обрыва потеряны), потоки не рвутся. Очередь потока —
    1000 событий, при переполнении — сброс и `resync`;
  - `GET /api/events` (sse-starlette): пользователь определяется своей сессией БД, которая закрывается до начала
    потока (открытая вкладка не держит соединение пула); нет LISTEN 5 с → 503. Поток начинается с `ready` (с этого
    момента подписка активна), дальше `event: <type>`, `data: <JSON data>` без `user_id`; keep-alive — комментарий
    раз в `SSE_PING_S` (15 с);
  - загрузка: `ingest.progress` при постановке в очередь (`queued`), при старте и возобновлении задачи
    (`processing`) и после пачки не чаще раза в 1 с (`Worker(progress_s=…)`); `ingest.done` — `status: done` или
    `failed`; поля `job_id, status, bytes_done, bytes_total, counts{new,duplicate,conflict,invalid}`, как в отчёте;
    `summary.updated {dates}` — при каждом сбросе «грязных» дат, в той же транзакции. `htadmin rebuild` событий
    не шлёт.
- **Последствия:** «не реже раза в 2 с» держится, пока пачка из 5000 записей обрабатывается быстрее 2 с. Frontend
  (шаг 5.2) на `resync` делает то же, что после переподключения EventSource: перезапрашивает всё. События целей,
  правил и настроек шлются через тот же `publish` на своих шагах. Описание — `docs/API.md`. Проверяется
  `integration/test_events.py` (7 тестов на настоящем uvicorn).

## ADR-041. Дашборд, устройства и «сегодня» с сервера
- **Дата:** 2026-10-11T11:20:14+06:00 (шаг 6.1)
- **Контекст:** SPEC §6.4, F2, F6, F7, F12, шаг 6.1 плана: дашборд дня и недели со сравнением и базами, графики с
  пропусками, страница устройств. Не определены: какой день открывать по умолчанию (время сервера идёт по `Clock`
  и может быть сдвинуто dev-панелью), что такое «последние данные» устройства, правила имени, нужно ли событие при
  переименовании, как рисовать пропуск на графике.
- **Варианты:** «сегодня» — по дате браузера или с сервера (`today` в `/api/auth/me`); «последние данные» — по исходным
  записям или по `coverage_minute`; переименование — без события (вторая вкладка увидит при следующем запросе) или с
  событием; пропуск — `null` как разрыв Recharts или отдельная форма столбца.
- **Выбор** (решение пользователя: «День по умолчанию — вариант 1 (today с сервера по Clock и истории поясов, поле в
  /api/auth/me). Допущения принимаю, кроме одного: событие при переименовании устройства нужно…»):
  - `today` в ответах `register`/`login`/`me` — локальная дата по `Clock` и истории поясов; dev-панель после сдвига
    перезапрашивает всё, кроме своих ключей, так что дашборд переходит на новый день сам;
  - день или неделя — в адресе (`/?date=2026-10-07`, `/?view=week&week=2026-W41`), без них — `today`; в режиме «День»

  - имя 1–100 символов после обрезки пробелов; `PATCH` публикует `devices.changed {device_id}` в той же транзакции,
    `useEvents` перезапрашивает `["devices"]`;
  - график — столбцы Recharts с собственной формой `GapBar`: день без значения рисуется штриховкой на всю высоту с

## ADR-043. Цели, достижения и уведомления
- **Дата:** 2026-10-11T13:19:02+06:00 (шаг 7.1)
- **Контекст:** SPEC F8, F12, §6.3, §7.1, шаг 7.1 плана. Не определены: с какого дня действует изменённая цель,
  когда цель считается выполненной при неполных данных, формат API целей, прогресса и колокольчика, как вторая
  вкладка узнаёт о прочтении уведомлений, что делать, если цель снижена ниже уже набранного значения.
- **Варианты:** цель действует с момента `valid_from` (часть дня по старой цели) или с его локальной даты; выполнение —
  только в полный день и валидную ночь или по любому значению; прочтение — без события (вторая вкладка увидит при
  следующем запросе) или с событием; снижение цели — ждать следующего пересчёта или проверять сегодняшний день сразу.
- **Выбор** (Допущения 1–7, приняты пользователем: «ок, допущения 1–7 принимаю.»):
  1. версия цели действует с **локальной даты** своего `valid_from` (по истории поясов): изменённая сегодня цель
     действует уже сегодня, прошлые дни — по своей. До первой версии — 8000 шагов и 8 ч (`valid_from: null`).
     `PUT` с теми же значениями новую версию не создаёт;
  2. `GET/PUT /api/goals` — `[{kind, target, valid_from}]`; тело `PUT` — `{steps, sleep}`, оба обязательны: шаги — целое
     100–100 000, сон — 1–16 ч (хранится `REAL`, показывается с округлением до 0,01). Событие `goal.changed {kinds}`;
  3. у каждого дня сводки `goals.{steps|sleep} = {target, percent, achieved}`: `percent` округлён вниз (100 — только
     при выполненной цели), у дня без значения — `null`; у недели и предыдущей недели — `goals.{kind} =
     {achieved_days, of: 7}`, каждый день — по своей цели;
  4. цель выполнена, если значение ≥ цели, при любом статусе дня и валидности ночи: неполные данные дают значение не
     больше настоящего, ложного достижения не будет. Сон — минуты сна дня пробуждения / 60;
  5. достижение записывается в конце **каждого пересчёта сводок** (`recompute_dates`: загрузка, `htadmin rebuild`,
     позже смена пояса) в той же транзакции: строка `goal_achievements` (первичный ключ — один раз на вид и дату),
     уведомление и события `notification.created {id, type}`, затем `goal.achieved {kind, local_date, target, value,
     show_toast, notification_id}`; `value` — шаги или часы с точностью 0,1; `show_toast` — дата сегодня или вчера по
     `Clock` и поясу пользователя;
  6. `GET /api/notifications?limit=50` → `{items, unread}` (новые сверху, `limit` ≤ 200); `POST /api/notifications/read`
     `{ids}` (≤ 100; без `ids` — все) → `{unread}`, чужие id не меняются и не дают ошибки. Новое событие
     `notifications.read {ids}` или `{all: true}` — счётчик колокольчика во второй вкладке (F12); в списке F12 его нет;
  7. `PUT /api/goals`, изменивший цель, сразу проверяет сегодняшний день: цель, сниженная до уже набранного значения,
     выполнена без новой загрузки (тост, колокольчик).
- **Последствия:** миграции 0007–0009 (`goals`, `notifications`, `goal_achievements`). Повышение цели не отменяет уже
  записанное достижение. Шаг 7.2: события `goal.achieved`, `notification.created`, `notifications.read`, `goal.changed` —
  строками в `handlers` `useEvents.ts`; тост — по `show_toast`. Проверяется `integration/test_goals.py` (10 тестов).

## ADR-046. Уточнение ADR-036 и SPEC F5: сессия сна на краю данных не относится ни к какому дню
- **Дата:** 2026-10-11T14:36:52+06:00 (шаг 8.1, исправление шага 4.3)
- **Контекст:** ручная проверка шага 8.1: после загрузки `short-sleep` до 10.10 сон 10.10 был 346 мин, после загрузки
  11.10 — 299. Файл кончается в 24:00 10.10, пользователь заснул в 23:13: по ADR-036 эти 47 минут были отдельной сессией
  с последней минутой 10.10 и попадали в 10.10. Из-за этого R1 могла ложно закрыться (ночь «≥ 7 ч»), цель по сну —
  ложно засчитаться, а значение дня менялось задним числом.
- **Варианты:** (а) как было — сессия на краю относится к дате последней минуты; (б) край — по окну, которое читает
  `compute_day` (конец дня + 2 ч); (в) край — по всем данным пользователя.
- **Выбор:** (в), решение пользователя: «Правило: сессия, после конца которой нет никаких данных ни с одного устройства
  (край загруженных данных), считается незавершённой и не относится ни к какому дню, пока не придёт продолжение»;
  «Край данных — по всем данным пользователя».
  - край данных — конец последней минуты, которую покрывает любое устройство пользователя (`metrics.data_end`,
    один индексный поиск на устройство); сессия, конец которой не раньше края, не входит ни в один день
    (`sleep.summarize_sleep`, параметр `data_end`); `recompute_dates` считает край один раз на вызов;
  - продолжение: следующие минуты сна продолжают сессию — она уходит в день своего настоящего пробуждения; любые
    данные после конца (шаги, пульс с любого устройства, хоть через несколько часов) завершают её — тогда она
    относится к дате своей последней минуты, как раньше;
  - грязные даты (`summaries.affected_dates`): к датам интервала добавляется дата последней покрытой минуты перед
    каждым интервалом — прежний край. Иначе данные, пришедшие после разрыва > 91 мин, не пересчитали бы день сессии,
    которая на старом краю теперь завершена.
- **Последствия:** SPEC F5 дополнен. Тест шага 7.1 `test_sleep_goal_counted_on_wake_day` загружал одну запись сна без
  данных после неё — добавлены шаги после пробуждения. Уже посчитанные сводки старых пользователей меняются только при
  пересчёте (`htadmin rebuild`); записанные достижения и рекомендации не отменяются (ADR-043, ADR-045). Полная пересборка
  совпадает с пошаговой (хеш `daily_summaries` на живом стеке). Тесты: `unit/test_sleep.py::
  test_session_cut_by_data_edge_belongs_to_no_day`, `::test_session_with_data_after_it_is_finished`,
  `integration/test_summaries.py::test_session_cut_by_data_edge_waits_for_continuation`,
  `::test_data_after_long_gap_recomputes_date_of_old_edge`.

## ADR-047. R3–R6, опорные даты, оценка правил раз в час
- **Дата:** 2026-10-11T15:14:20+06:00 (шаг 8.2)
- **Контекст:** SPEC F6, F9, шаг 8.2 плана. В SPEC не определены: по какому дню и какой базе закрывается R3; какой
  датой задаётся неделя R4 и как считается разница; как считать стандартное отклонение «по кругу суток» в R5 и в каком
  поясе время отбоя; каких пользователей и как оценивает часовой таймер воркера.
- **Варианты:** R3 — закрытие по последнему дню с пульсом (сколь угодно давнему) или по опорной дате; база закрытия —
  снимок при открытии, база перед опорной датой или база пары, кончающейся опорной датой. R5 — круговое отклонение
  `sqrt(-2 ln R)` или отклонение кратчайших разностей от кругового среднего. Таймер — задачи в очереди `jobs` или
  оценка прямо в цикле воркера; все пользователи или только те, у кого сменилась дата.
- **Выбор** (Допущения 1–8, приняты пользователем: «я посмотрел все нормально, продолжай»):
  1. R3: «последний день с посчитанным пульсом» — опорная дата (вчера); нет пульса — `unknown`. База и для срабатывания,
     и для закрытия — среднее 14 дат перед парой (опорная − 1, опорная), то есть [опорная − 15, опорная − 2], не меньше
     7 значений. Срабатывание — оба дня пары ≥ база + 7, закрытие — опорный день < база + 4;
  2. R4: опорная дата — воскресенье последней завершённой ISO-недели (в воскресенье текущая неделя не закончена — берётся
     прошлая); средние — по валидным ночам (как недельная сводка F7), не меньше 5 в каждой неделе. Разница = среднее
     позапрошлой − среднее прошлой: ≥ 60 — срабатывание, < 30 — закрытие (в том числе если сна стало больше), 30–59 —
     без изменений;
  3. R5: отбой — начало основной сессии в местном времени пояса, действовавшего в этот момент (`Facts.local_time` по
     истории поясов). Разброс — генеральное стандартное отклонение (делим на n) кратчайших по кругу разностей от
     кругового среднего: 23:30 и 00:30 — разница 60 мин, σ = 30 мин; совпадает с генератором («irregular» — σ = 120).
     Окно — 7 ночей, кончающихся опорной датой, учитываются только валидные (≥ 5). > 90 — срабатывание, < 60 — закрытие;
  4. R6: окно — 5 полных дней, кончающихся вчера; закрытие — полный опорный день с ≥ 15 активными минутами;
  5. оценка по таймеру: при старте воркера и затем раз в `RULES_TICK_S` (3600 с) — прямо в цикле воркера, не задачами
     очереди. Оцениваются пользователи со сводками за последние `LOOKBACK` + 1 дней (без данных все правила `unknown`);
     каждый — в своей транзакции под транзакционной advisory-блокировкой пользователя (`queue.try_lock_user`).
     Пользователь с выполняющейся задачей пропускается, а не ожидается: конец задачи сам оценит правила. Повторная
     оценка идемпотентна (машина состояний и `uq_recommendations_open`), поэтому дата не отслеживается;
  6. тест `test_evaluated_after_ingest_done` был зелёным с начала: вызов сделан на шаге 8.1 (ADR-045, п. 4);
  7. тест сценариев идёт путём пачек воркера (разбор → классификация → пересчёт дат → оценка) в откатываемой транзакции:
     16 дней по Москве до воскресенья, `--hr-interval 60`, оценка в 09:00 следующего утра; ожидаемые правила — подмножество

## ADR-049. Планировщик дайджеста: `plan_send` и `plan_send_time`, лимит по датам, просроченное время
- **Дата:** 2026-10-11T17:30:31+06:00 (шаг 9.1)
- **Контекст:** SPEC F10 задаёт `plan_send_time(pending, last_digest_local_date, tz_history, quiet_hours, now) → datetime`
  и порядок правил (окно и потолок → лимит «одно письмо в сутки» → тихие часы → лимит ещё раз), а `email_digests` хранит
  `plan_reason`. Не определены: откуда брать причину переноса, как сравнивать дату с датой последнего дайджеста, когда
  местная дата после перелёта на запад «идёт назад», что делать с уже прошедшим `T`, какая причина при нескольких сдвигах,
  в каком поясе считать конец тихих часов.
- **Варианты и выбор** (ответ пользователя — в PROMPTS.md, 2026-10-11T17:30:31+06:00):
  1. Причина переноса: (а) `plan_send_time` возвращает `SendPlan` вместо `datetime` — **не принято** (SPEC не меняем);
     (б) **`plan_send(...) → SendPlan(at, reason)` с основной логикой, `plan_send_time` с сигнатурой SPEC — обёртка,
     возвращает `plan.at`**. Окно и потолок — аргументы `plan_send` со значениями по умолчанию 15 и 60 минут; чтение
     `DIGEST_WINDOW_MINUTES` / `DIGEST_MAX_DELAY_MINUTES` из env — на шаге 9.2.
  2. Лимит: (а) нельзя только в ту же дату (`==`); (б) **дайджест уходит только на местную дату строго позже даты
     последнего дайджеста (`<=` блокирует)**: `T` переносится на первый момент после `T`, местная дата которого больше
     даты последнего дайджеста. Даты дайджестов только растут, `UNIQUE(user_id, local_date)` не срабатывает; цена —
     после перелёта на запад письмо ждёт дольше суток (Токио 12.10 → Нью-Йорк: 00:00 13.10 по Нью-Йорку). Принято.
  3. Просроченное время: **`T = max(T, now)`**, к нему применяются лимит и тихие часы (иначе просроченный дайджест ушёл
     бы в тихие часы). Принято. Уточнение по вопросу пользователя: если `T` сдвинут на `now` и дальше его ничего не
     двигает, причина остаётся той, что дало правило 1, — `window` или `max_delay`: сдвиг на «сейчас» — не перенос
     по правилу, отдельного значения в enum `plan_reason` SPEC нет.
  4. Причина — **последнее правило, сдвинувшее `T`** (лимит на 00:00, затем тихие часы на 08:00 → `quiet_hours`);
     правило 1 даёт `window`, если `последнее + WINDOW ≤ первое + MAX_DELAY`, иначе `max_delay`. Принято.
  5. Конец тихих часов — **в поясе, действующем в момент `T`**: будущих переездов в истории нет (ADR-017), поэтому
     после `now` пояс не меняется. Тихие часы — `[начало, конец)`; начало = конец — выключены (ADR-017). Принято.
- **Последствия:** `app/services/notify/planner.py` (`plan_send`, `plan_send_time`, `QuietHours`, `SendPlan`),
  тесты `unit/test_planner.py`: 11 тестов плана и сверх плана `test_local_date_going_back_after_move_west_still_limited`,
  `test_overdue_plan_moves_to_now_and_respects_quiet_hours`, `test_plan_send_time_returns_planned_time`. Диспетчер 9.2
  вызывает `plan_send` и пишет `at` и `reason` в `email_digests.planned_at` / `plan_reason`, а `last_digest_local_date` —
  наибольшая `local_date` отправленных дайджестов пользователя.

## ADR-050. Outbox, диспетчер дайджестов, письмо и Mailpit; исправление тихих часов при переводе часов
- **Дата:** 2026-10-11T18:15:04+06:00 (шаг 9.2)
- **Контекст:** SPEC F10 задаёт `email_outbox` (запись вместе с открытием рекомендации), диспетчер с тиком 30 с, одно
  письмо со всеми ожидающими, `email_digests` с `planned_at`/`plan_reason` и частичным уникальным индексом по
  `local_date`, тему «Трекер здоровья: N новых рекомендаций», предупреждение, если почта не указана. Не определены:
  где хранить ещё не отправленный план, как не отправить письмо дважды при нескольких воркерах и сбоях SMTP, где
  показывать предупреждение, что делать с грамматикой темы. Пользователь нашёл ошибку закрытого шага 9.1 (тихие часы
  в ночь перевода часов назад).
- **Варианты и выбор** (ответ пользователя — в PROMPTS.md, 2026-10-11T17:58:27+06:00):
  1. **Тема со склонением** — «1 новая рекомендация», «2 новые рекомендации», «5 новых рекомендаций». Это
     **отступление от буквального текста SPEC F10** («N новых рекомендаций»): буквальная форма неграмотна при 1–4
     (и 21–24, …). SPEC не меняется, решение — здесь (`services/notify/digest.py::new_recommendations`). Принято.
  2. **Предупреждение «нет почты»:** (а) отдельный эндпоинт; (б) **поле `warning: "no_notify_email"` в
     `GET /api/digests`** (плюс `notify_email`, `pending`). Письма не планируются, записи outbox остаются `pending`
     и уйдут одним письмом, когда почту укажут; строка дайджеста не создаётся. Принято. По указанию пользователя:
     SPEC требует предупреждение в интерфейсе, в plan.md оно ни на каком шаге не закреплено — добавлена заметка к
     шагу 10.1 «Для 10.1: предупреждение в UI, если notify_email пуст». На шаге 9.2 оно видно только на dev-панели.
  3. **Запланированный дайджест — строка `email_digests` с `sent_at IS NULL`**, не больше одной на пользователя
     (`uq_email_digests_planned`), диспетчер обновляет её каждый тик, удаляет, если отправлять нечего. При отправке
     `planned_at` — последний план до срока (если он не в будущем: тогда — новый план), а не момент тика;
     `local_date` — дата отправки. Принято.
  4. **Своя advisory-блокировка диспетчера** (`DIGEST_LOCK_NAMESPACE = 33`, try-lock): блокировка задач загрузки
     задерживала бы письма на всю загрузку. Второй диспетчер пропускает занятого пользователя. Принято.
  5. **SMTP внутри транзакции отправки** — принято при двух условиях пользователя:
     (а) **явный таймаут:** `SmtpMailer` ограничивает всю отправку `asyncio.timeout(SMTP_TIMEOUT_S)` (10 с, env) и
     передаёт тот же таймаут в `aiosmtplib`; зависший сервер не держит транзакцию и блокировку дольше;
     (б) **как сохраняется `error` при откате:** пользователь обрабатывается тремя транзакциями — «план» (строка
     запланированного дайджеста коммитится), «отправка» (skipped, письмо, `sent`, `sent_at`, `flush` уникального
     индекса до SMTP, SMTP, событие, коммит) и при ошибке «ошибка» — отдельная транзакция `UPDATE email_digests SET
     error = … WHERE id = … AND sent_at IS NULL`. Откат второй транзакции не трогает строку из первой, поэтому ошибка
     остаётся; следующий тик повторяет, успех очищает `error`. Тесты: `test_smtp_failure_rolls_back_send_and_keeps_error`,
     `test_hanging_smtp_cut_off_by_timeout` (сервер, который принимает соединение и молчит; таймаут 0,5 с).
     Остаточный риск: коммит упал после того, как SMTP принял письмо, → повтор письма (at-least-once).
  6. **`scripts/test.*` поднимают Mailpit вместе с Postgres** (в CI он уже сервис); фикстура падает с понятным
     сообщением, если Mailpit недоступен, а не пропускает тест. Принято.
  7. **`skipped` — без `digest_id`**; `sent` — с дайджестом, в который вошла. Принято.
  8. **Env:** `SMTP_HOST`/`SMTP_PORT` (compose — `mailpit:1025`), `SMTP_TIMEOUT_S`, `MAIL_FROM`, `APP_URL` (ссылка в
     письме), `DIGEST_WINDOW_MINUTES`/`DIGEST_MAX_DELAY_MINUTES` (прокинуты в compose для e2e), `DIGEST_TICK_S`. Принято.
  9. **Исправление шага 9.1** (`fix(notify)`, регрессионные тесты после кода): конец тихих часов — первый момент
     после планового времени, который не попадает в тихие часы. При переводе назад местное время конца бывает дважды
     (fold 0/1) — берётся проход после `at` (было: первый проход, раньше окна и `now`); при переводе вперёд время конца
     может не наступить — конец там, где часы перескакивают через него (поиск до секунды; было: на 30 мин позже),
     а если скачок съел всё свободное время ночи — конец тихих часов на следующую дату (было: `RuntimeError`; найдено
     property-тестом: Сантьяго, 06.09.2026, тихие часы 00:15–00:00).
     Инвариант (property-тест вокруг переводов 2026 г.): план не раньше окна/потолка и `now`, не в тихих часах, дата
     после последнего дайджеста.

## ADR-051. Настройки, история поясов и пересчёт после переезда
- **Дата:** 2026-10-11T18:58:01+06:00 (шаг 10.1)
- **Контекст:** SPEC F11 и §6.3 задают `GET/PATCH /api/settings` (почта, тихие часы), `GET/POST /api/settings/timezones`
  с «действует с» (по умолчанию сейчас, в будущем — 422, ADR-017), пересчёт затронутых дней и правил фоновой задачей
  (F5) и событие `settings.changed`; SPEC F10 — предупреждение в интерфейсе без почты (заметка шага 10.1, ADR-050).
  Не определены: в каком поясе читается «действует с», что делает переезд задним числом с более поздними записями,
  как найти затронутые даты, формат времени тихих часов.
- **Варианты и выбор** (допущения 1–6 приняты пользователем: «ок, допущения принимаю», PROMPTS.md):
  1. **«Действует с» без смещения — местное время нового пояса** («прилетел в 08:00 по Нью-Йорку»), со смещением —
     как есть; время в «дыре» перевода — со смещением до перевода (`fold=0`). Альтернатива — пояс браузера: путает,
     если браузер уже в новом поясе или ещё в старом. На странице поле `datetime-local` уходит строкой без смещения.
  2. **Переезд задним числом добавляет запись до следующей**, поздние записи не удаляются (иначе теряется история).
     Следствие: переезд раньше записи регистрации не меняет текущий пояс — это видно в истории «с … по …».
  3. **Тот же момент или пояс, который уже действует, — 409**; переезд раньше 1970 — 422.
  4. **Почта:** `""`/`null` — писем нет; тихие часы — строго `HH:MM`; начало = концу — выключены (ADR-017); PATCH
     меняет только переданные поля, лишнее поле → 422; событие — только при настоящем изменении, `{fields}`.
  5. **Пересчёт — задача `tz_changed` в общей очереди** с отрезком `[valid_from, valid_to)` (до следующей записи).
     Воркер пересчитывает даты отрезка по новой истории и существующие сводки за `[(начало − 12 ч).date(),
     (конец + 14 ч).date()]` — туда отрезок мог попасть по старой (локальная дата отличается от UTC не больше чем на
     −12/+14 ч), отрезок обрезается данными пользователя; затем `summary.updated` и `evaluate_user`, одной транзакцией
     под блокировкой пользователя. Варианты: хранить в задаче старый пояс (неверно, если до запуска задачи пришёл ещё
     один переезд в том же отрезке) или пересобирать всё (дорого). Выбран вариант без старой истории: задачи быстрых
     переездов покрывают друг друга в любом порядке; лишняя дата на краю пересчитывается впустую, но без вреда.
  6. **`timezone` в `/api/auth/me`**: время в интерфейсе (устройства, план дайджеста) — в поясе пользователя, а не
     браузера (заметка шага 6.1); время записей истории — по часам своего пояса.
  7. **Найдено при реализации (тесты `test_tz_change.py`):** первая запись по ADR-033 действует и до себя, поэтому
     переезд раньше всей истории (до записи регистрации) молча переносил в новый пояс и всё время до переезда, а
     пересчитывались только даты после него. По допущению 2 время до переезда не меняется: прежний первый пояс
     сохраняется записью с `HISTORY_START` (1970-01-01, в API `valid_from: null`, на странице «с начала истории»).
     Регрессионный тест — `test_move_before_history_keeps_earlier_zone` (после кода).
- **Последствия:** `api/settings.py`, `schemas/settings.py`, `services/timezones.py` (`entries`, `changed_dates`,
  `apply_tz_change`), обработчик `tz_changed` в `worker/handlers.py`; миграций нет. Frontend: страница «Настройки»
  (`pages/Settings.tsx`, `api/settings.ts`, `lib/settingsSchema.ts`, `lib/dates.ts::formatDateTime`), ключи
  `settingsKey`/`timezonesKey`, обработчик `settings.changed` в `useEvents.ts`, время устройств в поясе пользователя.
