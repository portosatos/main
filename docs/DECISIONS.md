## ADR-001. Стек backend: Python 3.12 + FastAPI + SQLAlchemy 2.0 async + PostgreSQL
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §1.1, §5; Python, FastAPI и PostgreSQL утверждены заказчиком)
- **Контекст:** нужен отдельный backend на Python с PostgreSQL (§1.1 п. 2–3), массовая загрузка телеметрии,
  расчёт временных рядов, SSE, автоматическая документация API как доказательство работы.
- **Варианты:** (а) Django + DRF; (б) Flask; (в) FastAPI + SQLAlchemy 2.0 async + asyncpg + Alembic.
- **Выбор:** (в). Async-стек естественен для SSE и фонового воркера; Pydantic v2 валидирует вход;
  `/docs` (OpenAPI) — наглядная проверка API; SQLAlchemy Core и `COPY` дают быструю массовую вставку;
  Alembic — стандарт миграций и место для `CREATE EXTENSION btree_gist`. Пароли — argon2-cffi (argon2id),
  пояса — zoneinfo + tzdata, логи — structlog, пакеты — uv, тесты — pytest + hypothesis на настоящем Postgres.
- **Последствия:** весь backend async; интеграционные тесты требуют поднятого Postgres (тестовая БД).

## ADR-003. Очередь задач в PostgreSQL вместо Redis/Celery
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §5, §6.1, §7.1)
- **Контекст:** загрузка, пересчёты, правила и письма выполняются в фоне. Нужна надёжность: постановка задачи
  атомарна с изменением данных, задачи не теряются при падении воркера.
- **Варианты:** (а) Celery + Redis; (б) RQ/arq + Redis; (в) своя очередь `jobs` в Postgres:
  `FOR UPDATE SKIP LOCKED`, пробуждение через `LISTEN/NOTIFY`, возврат зависших задач по `locked_at` > 5 мин.
- **Выбор:** (в). Меньше сервисов, постановка в очередь в той же транзакции, проще локальный запуск на Windows.
  Последовательность задач одного пользователя — advisory lock по `user_id`.
- **Последствия:** свой код очереди и тесты на него (возобновление, зависшие задачи, параллельность пользователей).

## ADR-004. SSE для событий в реальном времени
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC §5, F12)
- **Контекст:** изменения (прогресс, сводки, цели, рекомендации, настройки) должны появляться во всех вкладках
  пользователя ≤ 2 с. Поток нужен только от сервера к клиенту.
- **Варианты:** (а) polling; (б) WebSocket; (в) SSE (sse-starlette) + Postgres `NOTIFY` в канал `user_events`,
  каждый процесс API делает `LISTEN`.
- **Выбор:** (в). Cookie-авторизация работает «из коробки», EventSource сам переподключается, события между
  воркером и API идут через ту же БД. Полезная нагрузка — идентификаторы и даты, ≤ 8 КБ (лимит NOTIFY).
- **Последствия:** в nginx `proxy_buffering off`; фронтенд по событию инвалидирует ключи TanStack Query и делает
  полный refetch после переподключения.

## ADR-005. Исходные записи — источник истины, минутные таблицы — производный кеш
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.1, F4.3)
- **Контекст:** интервалы шагов приходят с произвольными, в том числе невыровненными границами; данные нужно
  уметь пересчитать при смене правил, поясов и после ошибок.
- **Варианты:** (а) хранить только агрегаты; (б) раскладывать в минуты при приёме и выбрасывать исходное;
  (в) хранить исходные записи (`steps_raw` с exclusion constraint на `btree_gist`, `sleep_raw`, `hr_point`) и
  считать из них `steps_minute`, `sleep_minute`, `coverage_minute` пропорциональными вкладами.
- **Выбор:** (в). Ничего не теряется на невыровненных интервалах; производные пересобираются
  (`htadmin rebuild`), пересчёт идемпотентен («удалить диапазон и вставить расчёт»).
- **Последствия:** больше места в БД; property-тест «сумма минут = сумма исходных».

## ADR-006. Классификация входящих записей new / duplicate / conflict / invalid
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.2)
- **Контекст:** повторная и частично пересекающаяся загрузка не должна менять итоги, а отчёт должен объяснять,
  что произошло с каждой записью.
- **Варианты:** (а) upsert «последний побеждает»; (б) молча игнорировать совпадения; (в) staging-таблица,
  схлопывание дублей внутри пачки и ровно один класс на запись; при конфликте побеждает первая загруженная
  запись (допущение SPEC).
- **Выбор:** (в). Загрузка идемпотентна, конфликты видны в отчёте (первые 50 с номером строки и причиной).
- **Последствия:** счётчики `new/duplicate/conflict/invalid` в `ingest_jobs`; разбор конфликтов в UI — «потом».

## ADR-007. Объединение устройств по минутам: часы важнее телефона
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F4.4, утверждено заказчиком)
- **Контекст:** часы и телефон пишут одну и ту же прогулку; сумма даст двойной счёт, а «максимум за день» потеряет
  прогулки, записанные только одним устройством.
- **Варианты:** (а) сумма; (б) максимум по дню; (в) приоритет устройства на уровне дня; (г) приоритет на уровне
  минуты: если минута покрыта часами — значение часов (0, если шагов нет), иначе телефона.
- **Выбор:** (г). Значение каждой минуты взято ровно с одного устройства, функция возвращает и `source_device_id`
  для проверки инварианта. Среди устройств одного типа приоритет у зарегистрированного раньше (допущение).
- **Последствия:** дневной итог может законно превышать итог любого устройства по отдельности; описание в
  `docs/MERGE_RULES.md`, property-тест инварианта.

## ADR-008. Сон относится к дню пробуждения
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F5, утверждено заказчиком)
- **Контекст:** ночной сон пересекает полночь; нужно однозначно отнести его к одной локальной дате.
- **Варианты:** (а) к дню засыпания; (б) делить по полуночи; (в) к дню пробуждения (как Garmin).
- **Выбор:** (в). Сессия — подряд идущие минуты сна с разрывами ≤ 30 мин, длиной ≥ 30 мин; засчитывается в дату
  окончания; основная сессия — самая длинная. Валидность ночи (`night_valid`) не зависит от статуса дня.
- **Последствия:** цель по сну и R1/R5 считаются по дню пробуждения.

## ADR-009. История часовых поясов пользователя
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F5)
- **Контекст:** пользователь путешествует; смещения в данных могут не совпадать с тем, как он хочет видеть дни.
  В день переезда ничего не должно теряться и удваиваться.
- **Варианты:** (а) один текущий пояс; (б) пояс из смещений в данных; (в) история `user_timezones(tz, valid_from)`
  из настроек; локальная дата события — по поясу, действовавшему в момент события.
- **Выбор:** (в). Каждое событие относится ровно к одной дате; сутки могут длиться 21–27 часов или состоять из
  двух кусков. Локальные даты считает только `services/localtime.py`.
- **Последствия:** смена истории запускает фоновый пересчёт затронутых дат и правил; описание в `docs/TIMEZONES.md`.

## ADR-010. Планировщик дайджеста — чистая функция `plan_send_time`
- **Дата:** 2026-10-10T17:28:48+06:00 (решение из SPEC F10)
- **Контекст:** письма: окно 15 мин, потолок 60 мин, не больше одного дайджеста в локальные сутки, тихие часы
  через полночь, смена пояса. Комбинации легко сломать.
- **Варианты:** (а) логика внутри диспетчера с БД и SMTP; (б) cron в фиксированное время; (в) чистая функция
  `plan_send_time(pending, last_digest_local_date, tz_history, quiet_hours, now)` + outbox + диспетчер раз в 30 с.
- **Выбор:** (в). Функция тестируется исчерпывающе без БД и SMTP; защита от повторов —
  `UNIQUE(user_id, local_date) WHERE sent_at IS NOT NULL`; причина переноса сохраняется в `email_digests`.
- **Последствия:** лимит и тихие часы сильнее потолка; после сдвига в тихие часы лимит проверяется повторно.

## ADR-014. Тесты до кода через strict-xfail
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 4)
- **Контекст:** заказчик хочет видеть по истории, что тесты появились раньше кода. Но `CLAUDE.md` §3 запрещает
  коммит с красными тестами.
- **Варианты:** (а) тесты и код одним коммитом — порядок не виден; (б) коммит красных тестов — нарушает
  `CLAUDE.md`; (в) коммит тестов с маркером ожидаемого падения: pytest `xfail(strict=True)`, Vitest `test.fails`,
  Playwright `test.fail()`; маркеры снимаются в коммите `feat(...)`.
- **Выбор:** (в). Strict-xfail на прошедшем тесте — ошибка, поэтому забыть снять маркер нельзя.
  Ответ пользователя: «Да, удачное решение: в истории будет видно, что тесты появились раньше кода».
- **Последствия:** коммит `test(<scope>): … (red)` не считается красным; `check_process.py` требует коммит
  `test(...)` раньше первого `feat(...)` шага; в WORKLOG пишутся сводки `N xfailed` и `N passed`.

## ADR-019. Проверка снятых xfail-маркеров не смотрит в `docs/`
- **Дата:** 2026-10-10T17:48:01+06:00
- **Контекст:** общий Done When плана проверял `git grep -n "step <X.Y>: not implemented"` → пусто. На шаге 0.1
  команда нашла строку в `docs/WORKLOG.md`, где агент цитировал эту же команду. Маркеров в коде не было, но пункт
  формально не выполнялся, а WORKLOG только дополняется — исправить запись нельзя.
- **Варианты:** (а) никогда не цитировать строку в журналах; (б) исключить `docs/` из поиска:
  `git grep -n "step <X.Y>: not implemented" -- ":!docs"`; (в) искать только в каталогах с тестами.
- **Выбор:** (б): маркеры живут только в коде и тестах, `docs/` их не содержит; (в) пришлось бы обновлять
  при появлении каждого нового каталога. Ответ пользователя: «Команду проверки маркеров в плане меняй, как
  предлагаешь (исключить docs)».
- **Последствия:** изменены общий Done When в `docs/plan.md` и `CLAUDE.md` §3.
