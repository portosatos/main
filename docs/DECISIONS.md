# DECISIONS — журнал решений (ADR)

Каждая запись: номер, дата и время (системное время записи), контекст, рассмотренные варианты, выбор и причина,
последствия. Номера не переиспользуются. Если решение отменяется, добавляется новый ADR со ссылкой на старый.

- ADR-001…ADR-010 — решения, зафиксированные в `docs/SPEC.md` (стек, архитектура, модель данных).
- ADR-011…ADR-018 — решения, утверждённые вместе с планом `docs/plan.md` (2026-10-10T16:59:35+06:00),
  раздел «Принятые решения», № 1–8. Ответы пользователя дословно — в `docs/PROMPTS.md`.

## ADR-011. Шаблон шага плана
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 1)
- **Контекст:** §8 SPEC описывает этапы крупно. Чтобы агент работал предсказуемо, у каждой порции работы нужны
  единые поля: цель, объём, тесты до кода, проверяемые критерии готовности, ручная проверка, границы.
- **Варианты:** (а) работать прямо по §8 SPEC; (б) свободный план без шаблона; (в) шаблон шага
  «Этап SPEC · Зависит от · Критерии §9 / Цель / Объём / Тесты до кода / Done When / Ручная проверка /
  Не делаем на этом шаге».
- **Выбор:** (в). Ответ пользователя: «Принять шаблон агента, он хороший».
- **Последствия:** каждый шаг `docs/plan.md` оформлен по шаблону; Done When — команды и тесты, которые можно
  выполнить; «Не делаем» защищает от расползания шага.

## ADR-012. Один шаг — одна сессия, остановка после каждого шага, `Stage: X.Y`
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 2)
- **Контекст:** `CLAUDE.md` требовал остановку и «дальше» в конце этапа и строку `Stage: N` в коммитах.
  Этапы §8 слишком велики для одной сессии агента: контекст сжимается, растёт риск потерять нить.
- **Варианты:** (а) этап за сессию, остановка после этапа; (б) шаг `X.Y` за сессию, остановка после каждого шага.
- **Выбор:** (б). Источник порядка работ — `docs/plan.md`; в коммитах `Stage: X.Y` (номер шага).
  Ответ пользователя: «Да. Это и есть «новая сессия на шаг»».
- **Последствия:** `CLAUDE.md` §1–§3 переписаны под шаги; WORKLOG ведётся записями «Шаг X.Y начат / завершён»;
  `scripts/check_process.py --step X.Y` проверяет коммиты и записи шага. Больше остановок, но каждая сессия
  маленькая и проверяемая.

## ADR-013. Frontend unit-тесты: Vitest + React Testing Library + MSW
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 3)
- **Контекст:** в стеке SPEC §5 для frontend были только Playwright e2e. Тогда у UI-шагов не было бы
  «тестов до кода» до этапа 12.
- **Варианты:** (а) только Playwright; (б) Jest + RTL; (в) Vitest + RTL + MSW.
- **Выбор:** (в). Vitest нативно работает с конфигом Vite (без отдельного бандлинга под Jest), RTL проверяет
  поведение, MSW подменяет API на уровне сети, поэтому код API-клиента тестируется как есть.
  Ответ пользователя: «Да, иначе у UI-шагов не будет тестов до кода».
- **Последствия:** строка в SPEC §5, `src/test/` и `*.test.tsx` в SPEC §6.2; `npm run check` включает vitest.

## ADR-014. Тесты до кода через strict-xfail
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 4)
- **Контекст:** заказчик хочет видеть по истории, что тесты появились раньше кода. Но `CLAUDE.md` §3 запрещает
  коммит с красными тестами.
- **Варианты:** (а) тесты и код одним коммитом — порядок не виден; (б) коммит красных тестов — нарушает
  `CLAUDE.md`; (в) коммит тестов с маркером ожидаемого падения: pytest `xfail(strict=True)`, Vitest `test.fails`,
  Playwright `test.fail()`; маркеры снимаются в коммите `feat(...)`.
- **Выбор:** (в). Strict-xfail на прошедшем тесте — ошибка, поэтому забыть снять маркер нельзя.
  Ответ пользователя: «Да, удачное решение: в истории будет видно, что тесты появились раньше кода».
- **Последствия:** коммит `test(<scope>): … (red)` не считается красным; `check_process.py` требует коммит
  `test(...)` раньше первого `feat(...)` шага; в WORKLOG пишутся сводки `N xfailed` и `N passed`.

## ADR-015. Ручные проверки SPEC в Done When заменены тестами; ручная проверка пользователем остаётся
- **Дата:** 2026-10-10T17:28:02+06:00 (утверждено 2026-10-10T16:59:35+06:00, решение плана № 5)
- **Контекст:** в SPEC часть критериев проверялась только руками: §8 этапы 5–6 (две вкладки, сводка по ходу
  обработки), §9 #6 (файл ~200 МБ), §9 #21 (контейнеры стартуют на Windows). Такие пункты агент не может честно
  отметить выполненными.
- **Варианты:** (а) оставить ручные пункты в Done When; (б) заменить их тестами и командами и отказаться
  от ручной проверки; (в) заменить в Done When, а ручную проверку пользователем оставить отдельным обязательным
  разделом отчёта.
- **Выбор:** (в): `test_events.py` и smoke SSE (этап 5), тест «сводки до завершения задачи» и e2e №2 (этап 6),
  `scripts/bench_ingest.ps1` (#6), `scripts/fresh_clone_check.ps1` (#21). Ответ пользователя: «Да. Но руками
  всё равно проверяйте сами, это пункт вашей схемы».
- **Последствия:** в каждом отчёте раздел «Проверьте руками»; «дальше» — только после неё; факт записывается
  в WORKLOG. Правки в `CLAUDE.md` §2, SPEC §8 (этапы 5, 6, 13), §9 #6, #21.
