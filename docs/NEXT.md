# Что дальше (не в MVP)

Что сделали бы следующим заходом. Сначала — найденное по ходу работы и при документировании (шаг 13.2), с шагом, на
котором нашли; затем список «Потом» из SPEC §3.2. Текущее состояние — [STATUS](STATUS.md).

## Найдено по ходу работы

### Параллельная обработка разных пользователей в стеке по умолчанию (шаг 3.2, ADR-031)
- **Сейчас:** в `docker-compose.yml` один процесс воркера, а он берёт одну задачу за раз. Поэтому в стеке по
  умолчанию задачи разных пользователей тоже идут по очереди: большой файл одного пользователя задерживает
  загрузку другого. Код к параллельности готов (`SKIP LOCKED` и advisory lock по пользователю, тест
  `test_same_user_jobs_sequential_different_users_parallel` с тремя воркерами), но её даёт только запуск
  нескольких процессов: `docker compose up -d --scale worker=2` (на стеке не проверялось).
- **Варианты:** несколько воркеров в compose по умолчанию (`deploy.replicas`); или N параллельных задач внутри
  одного процесса воркера (по соединению с advisory lock на задачу).
- **Учесть:** нагрузку на Postgres при нескольких одновременных загрузках; `worker_id` у реплик (сейчас
  `hostname-pid`, у реплик hostname разный).

### Видимые пропуски из `--gap-prob` (шаг 6.1, 13.2)
- **Сейчас:** случайный пропуск генератора выпадает у одного устройства, второе его закрывает, и на дашборде
  «нет данных» не видно (критерий §9 #3 — «частично», [STATUS](STATUS.md)). Видимый пропуск даёт только явный
  `--gap FROM/TO` без `@device`.
- **Варианты:** опция `--gap-scope all|device` для `--gap-prob`; или показывать на дашборде покрытие по устройствам
  (часы были сняты N часов), а не только итог по объединённым минутам.

### Запас по времени обработки большого файла (шаг 13.1)
- **Сейчас:** 197 МБ — 237 с при ориентире 300 с; postgres во время обработки ~2 ГиБ.
- **Варианты:** `COPY` вместо пачек `INSERT` в исходные таблицы; пересчёт минут по диапазонам пачки одним запросом;
  настройка `work_mem`/`shared_buffers` postgres в compose.

### Ручные проверки пользователем шагов 13.1 и 13.2
- Загрузка ~200 МБ через UI, `scripts/demo.ps1` с нуля и прохождение README в чистой папке ещё не подтверждены.

## Из SPEC §3.2 «Потом»
- Редактирование порогов правил и пользовательские правила (сейчас пороги — `PARAMS` в `services/rules/r*.py`).
- Ручной выбор приоритетного устройства и стратегии объединения в настройках (сейчас часы важнее телефона, ADR-007).
- Интерфейс для разбора конфликтов загрузки: выбрать, какую версию записи оставить (сейчас остаётся первая, ADR-006).
- Восстановление пароля, подтверждение email, ограничение частоты попыток входа, блокировка после N неудачных входов.
- Стадии сна, SpO2, калории, вариабельность пульса.
- Экспорт данных (CSV/JSON), удаление данных за период, удаление устройства с данными.
- Отдельное письмо о закрытии рекомендации; настраиваемые окно, потолок и время дайджеста (сейчас — переменные
  окружения `DIGEST_WINDOW_MINUTES`, `DIGEST_MAX_DELAY_MINUTES`).
- PWA и web push-уведомления.
- Интеграции с Apple Health, Google Fit, Garmin Connect.
- Продовое развёртывание: HTTPS, бэкапы, мониторинг, метрики Prometheus.
