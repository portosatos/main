## 1. Описание проекта и цель

Веб-приложение «Трекер здоровья», построенное по схеме клиент–сервер. Оно:
- принимает телеметрию с носимых устройств: **файлом NDJSON** или **потоком** (пачки записей по HTTP).
  Типы данных: **сон** (интервалы), **шаги** (интервалы), **пульс** (точки);
- объединяет данные с нескольких устройств одного пользователя (часы и телефон) без дублей и двойного счёта;
- считает дневные и недельные сводки и сравнивает их с предыдущим периодом;
- отслеживает цели (шаги в день, часы сна) и показывает прогресс;
- выдаёт рекомендации по фиксированному набору правил, без LLM. Рекомендации видны в интерфейсе и приходят
  на почту дайджестом (не больше одного письма в сутки) с учётом тихих часов.

Это **тестовое задание** («Задание 2. Трекер здоровья»). Кроме работающего продукта, результат должен
**доказывать свою работоспособность** (тесты, демо-скрипт, письма в Mailpit) и **прозрачно показывать процесс**:
коммиты, журнал работы, решения, экспорт сессии.

## 2. Целевая аудитория и сценарии использования

**Аудитория:**
- условный пользователь носимых устройств, который хочет видеть сводку по сну, активности и пульсу и получать советы;
- проверяющие тестового задания: им нужно быстро поднять проект, загрузить тестовые данные и увидеть
  все обязательные сценарии.

**Основные сценарии:**
1. **Регистрация и вход.** Пользователь регистрируется по email и паролю и попадает на дашборд.
   В сиде есть демо-пользователь.
2. **Загрузка большого файла.** Пользователь генерирует файл за 90 дней с двух устройств и загружает его.
   Он видит прогресс загрузки, затем прогресс обработки. Интерфейс остаётся отзывчивым, сводка на дашборде
   заполняется по мере обработки.
3. **Повторная загрузка.** Пользователь загружает тот же файл или файл, частично пересекающийся с прежним.
   Итоги не меняются, в отчёте загрузки видно, сколько записей новых, сколько дубликатов и сколько конфликтов.
4. **Поток.** Генератор в режиме `--stream` шлёт пачки записей в API. Дашборд обновляется в реальном времени.
5. **Просмотр сводок.** День или неделя: сон, шаги, активные минуты, пульс в покое и пиковый, разница
   с предыдущим периодом. Дни без данных отмечены как «нет данных», неполные дни — как «неполные данные».
6. **Цели.** Пользователь задаёт цели по шагам и сну и видит прогресс. Как только пришли данные, по которым цель
   достигнута, появляется уведомление.
7. **Рекомендации.** Правило сработало: рекомендация появляется в интерфейсе и попадает в ежедневный
   письмо-дайджест (не больше одного письма в сутки, в тихие часы письмо откладывается). Когда ситуация
   исправилась, рекомендация закрывается сама. Пользователь отмечает рекомендации как «полезно» или «не полезно».
8. **Правила.** Пользователь видит список правил с описанием и отключает ненужные. История рекомендаций
   по отключённому правилу сохраняется.
9. **Настройки.** Почта для писем, часовой пояс с датой и временем смены (поездка), тихие часы.
10. **Две вкладки.** Действие в одной вкладке (загрузка, отключение правила, отметка «полезно», смена настроек)
    сразу отражается во второй.

## 3. Функциональные требования

### 3.1. MVP

#### F0. Служебное время (Clock)
- Абстракция `app.clock.Clock`, реализуется **на этапе 1**. Через неё весь backend получает «сейчас»: цели,
  правила, письма, тихие часы, сессии, опорные даты.
- В dev-режиме (`APP_ENV=dev`) у часов есть сдвиг, который хранится в таблице `dev_clock` и меняется через
  `POST /api/dev/clock` и dev-панель в интерфейсе. Нужен для демо и e2e: смена суток, тихие часы, окно и
  потолок дайджеста без ожидания. В prod-режиме эндпоинт выключен, сдвиг игнорируется.
- Воркер и API читают сдвиг из БД, поэтому время у них согласовано.

#### F1. Учётные записи
- Регистрация (email и пароль от 8 символов), вход, выход, получение текущего пользователя (`/api/auth/me`).
  Допущение (утверждено пользователем, ADR-017): в теле регистрации frontend передаёт пояс браузера
  (`Intl.DateTimeFormat().resolvedOptions().timeZone`); он становится первой записью истории поясов (F5).
  Невалидный IANA-пояс → 422.
- Сессия хранится на сервере (таблица `sessions`). В браузере лежит только случайный токен в cookie
  `ht_session` с флагами `HttpOnly`, `SameSite=Lax`, а в prod-режиме ещё `Secure`. Срок жизни — 14 дней.
- Пароли хешируются argon2id.
- Защита от CSRF: `SameSite=Lax` и обязательный заголовок `X-Requested-With: ht` на всех изменяющих запросах.
- Демо-пользователь из сида: `demo@example.com`, пароль задаётся в `.env.example`.
- Допущение: восстановления пароля и подтверждения почты нет.
- Допущение: логин — это email. Почта для писем — отдельное поле в настройках, по умолчанию совпадает с логином.

#### F2. Устройства
- Устройство принадлежит пользователю: `external_id` из данных, тип `watch` или `phone`, имя.
- Устройства создаются автоматически при первой встрече в данных: тип берётся из meta-строки файла (раздел 7.2).
  Также их можно посмотреть и переименовать на странице «Устройства».
- Допущение: у устройств нет отдельных токенов. Данные загружает авторизованный пользователь.

#### F3. Приём данных
- **Файл:** `POST /api/ingest/files` (multipart). Файл потоково пишется на диск в volume, создаётся задача
  `ingest_job`, ответ `202` с `job_id`. Обработку выполняет **воркер**, а не HTTP-запрос.
- **Поток:** `POST /api/ingest/batch` принимает JSON-массив тех же записей, до 5000 за раз. Записи кладутся
  в задачу и обрабатываются тем же конвейером. Ответ `202`.
- Парсинг NDJSON построчный, память не зависит от размера файла. Записи обрабатываются пачками по 5000
  (классификация и вставка — см. F4).
- Битая строка не роняет загрузку. Она считается ошибкой (`invalid`), первые 50 ошибок и конфликтов
  сохраняются в задаче с номером строки и причиной.
- Прогресс = обработанные байты / размер файла. События о прогрессе приходят по SSE не реже раза в 2 секунды.
- По ходу обработки, не реже раза в ~2 секунды, пересчитываются производные данные для затронутых диапазонов
  («грязные» устройства, интервалы и даты) и отправляется событие `summary.updated`. Поэтому **сводка обновляется
  по мере обработки**.
- Отчёт по задаче: статус (`queued`, `processing`, `done`, `failed`), всего записей, `new`, `duplicate`,
  `conflict`, `invalid`, время начала и конца.
- Воркер упал посреди файла: задача продолжается с сохранённого смещения в байтах. Повтор безопасен благодаря
  идемпотентности. Записи, уже вставленные до падения, при повторе считаются `duplicate`, а итоговые данные
  не меняются.
- Допущение: у одного пользователя задачи обрабатываются строго по очереди (advisory lock по `user_id`).
  Задачи разных пользователей идут параллельно.
- Допущение: лимит размера файла — 500 МБ.

#### F4. Хранение, дедупликация и объединение устройств
Всё хранится в **UTC**. Смещение в метке времени (`+03:00`) нужно только для перевода в UTC.

**4.1. Исходные записи — источник истины.** Записи хранятся как пришли:
- `steps_raw(device_id, start_utc, end_utc, count)`, первичный ключ `(device_id, start_utc, end_utc)`.
  Дополнительно — exclusion constraint (расширение `btree_gist`):
  `EXCLUDE USING gist (device_id WITH =, tstzrange(start_utc, end_utc, '[)') WITH &&)`.
  Интервалы одного устройства не пересекаются, соседние (`[)`) разрешены.
- `sleep_raw(device_id, start_utc, end_utc)`, первичный ключ `(device_id, start_utc, end_utc)`.
  Пересечения интервалов сна одного устройства разрешены: сон объединяется как множество минут, двойного
  счёта не бывает.
- `hr_point(device_id, ts_utc, bpm)`, первичный ключ `(device_id, ts_utc)`.
- У каждой записи есть `ingest_job_id` и `ingested_at`, чтобы было видно её происхождение.

**4.2. Классификация каждой входящей записи.** Пачка кладётся во временную staging-таблицу, внутри пачки дубли
по ключу схлопываются, затем каждая запись получает ровно один класс:

| Класс | Условие | Действие |
|---|---|---|
| `new` | Записи с таким ключом нет, конфликтов нет | Вставляется |
| `duplicate` | Есть запись с тем же ключом **и теми же значениями** (`count`, `bpm`) | Пропускается |
| `conflict` | Тот же ключ, но другое значение; **или** (только шаги) интервал пересекается с уже сохранённым интервалом того же устройства с другими границами | Отклоняется, попадает в ошибки задачи |
| `invalid` | Не прошла валидацию (раздел 7.2) | Отклоняется, попадает в ошибки задачи |

Допущение: при конфликте **побеждает первая загруженная запись**. Генератор конфликтов не создаёт, это защита
от испорченных или перевыгруженных с другой нарезкой данных. Счётчики `new`, `duplicate`, `conflict`, `invalid`
показываются в отчёте загрузки.

**4.3. Производные минутные таблицы.** Это кеш: он пересчитывается из исходных записей для затронутых диапазонов
времени устройства командой «удалить диапазон и вставить расчёт». Пересчёт идемпотентен.
- `steps_minute(device_id, minute_utc, steps real)`. Значение минуты — **сумма вкладов всех интервалов устройства**,
  пересекающих эту минуту. Вклад интервала = `count × (секунды пересечения с минутой) / (длина интервала в секундах)`.
  Интервалы одного устройства не пересекаются, поэтому сумма корректна и **ничего не теряется**. Пример:
  `08:00:30–08:01:30` (60 шагов) и `08:01:30–08:02:30` (60 шагов) → 08:00 = 30, **08:01 = 30 + 30 = 60**,
  08:02 = 30.
- `sleep_minute(device_id, minute_utc)` — минута отмечена, если интервалы сна устройства покрывают ≥ 30 секунд
  этой минуты. Допущение.
- **Покрытие:** устройство «покрывает» минуту, если хоть одна его исходная запись (интервал шагов, интервал сна,
  точка пульса) пересекается с этой минутой.

**4.4. Правило объединения устройств: часы важнее телефона** (утверждено заказчиком). Работает **на уровне минуты**:
- **Шаги за минуту:** если минута покрыта часами, берётся значение часов (если записей шагов нет — 0).
  Иначе берётся значение телефона. Если не покрыта ни одним устройством, данных нет.
  **Инвариант:** значение каждой минуты всегда взято ровно с одного устройства и никогда не равно сумме
  нескольких. Функция объединения возвращает и значение, и `source_device_id`, чтобы инвариант можно было
  проверить тестом.
- Следствие: если одну прогулку записал только телефон (часы сняты), а другую оба устройства, дневной итог
  законно **больше**, чем у любого устройства по отдельности. Это корректно.
- **Сон за минуту:** если минута покрыта часами, учитывается состояние сна по часам, иначе по телефону.
- **Пульс:** используются точки часов. Точки телефона берутся только в минуты, где у часов пульса нет.
- Если у пользователя несколько устройств одного типа, приоритет у того, что зарегистрировано раньше.
  Допущение.
- Правило описано в `docs/MERGE_RULES.md` с примерами и покрыто unit-тестами.

#### F5. Атрибуция по дням и часовые пояса
- У пользователя есть **история часовых поясов**: `user_timezones(tz IANA, valid_from_utc)`. Если пользователь
  меняет пояс в настройках, добавляется новая запись. По умолчанию она действует с текущего момента (`Clock`),
  но можно указать прошлые дату и время переезда.
  - Допущение (утверждено пользователем, ADR-017): первая запись истории создаётся при регистрации из пояса
    браузера (F1), `valid_from` — момент регистрации по `Clock`.
- **Локальная дата события** — календарная дата в поясе, который действовал в момент события.
  Каждое событие относится ровно к одной дате, поэтому в день переезда **ничего не теряется и не удваивается**.
  Сутки при этом могут длиться 21 или 27 часов либо состоять из двух кусков. Это нормально и описано
  в `docs/TIMEZONES.md`.
  - Допущение: пояс для подсчёта дней берётся **из настроек пользователя**, а не из смещений в данных.
- **Сон относится к дню пробуждения**, как у Garmin (утверждено). Сессия сна — это подряд идущие минуты сна
  после объединения, с разрывами не больше 30 минут. Сессия засчитывается в локальную дату своего **окончания**.
  - Допущение: учитываются сессии от 30 минут. «Основная» сессия дня — самая длинная, по ней определяются
    время отбоя и подъёма.
- При изменении истории поясов затронутые даты пересчитываются фоновой задачей.

#### F6. Пропуски, полнота дня, валидность ночи
- **Время ношения** за день — число минут, которые покрыты хотя бы одним устройством.
- Статус дня:
  - `no_data` — 0 минут. В интерфейсе «нет данных», **не 0 шагов и не 0 сна**;
  - `partial` — от 1 до 719 минут. Значения показываются с пометкой «неполные данные (носили N ч)»;
  - `complete` — **от 12 часов** (утверждено).
- **Валидная ночь** (`night_valid`). Это признак сна, **не зависящий от статуса дня**. Допущение:
  основная сессия существует, в 60 минутах до её начала и в 60 минутах после конца есть данные, а внутри сессии
  нет пропусков данных длиннее 30 минут. Так снятые посреди ночи часы не превращаются в «короткий сон».
  Ночь может быть валидной даже в день со статусом `partial` (ночь записана целиком, днём часы почти не носили).
- **На отсутствующих данных правила не срабатывают и не закрываются.** Ситуация считается неизвестной,
  состояние рекомендации не меняется. Что считать «данными» для каждого правила, указано в F9.
- На графиках дни `no_data` — пустой столбец со штриховкой и подписью, а не ноль.

#### F7. Метрики и сводки
За локальную дату D (таблица `daily_summaries`, пересчитывается при поступлении данных):
- `steps` — сумма шагов по объединённым минутам; `null`, если `no_data`;
- `sleep_minutes` — сон в сессиях, закончившихся в день D; `sleep_start` и `sleep_end` основной сессии;
  `night_valid`;
- `active_minutes` — минуты, в которые после объединения не меньше 100 шагов;
- `resting_hr` — **10-й перцентиль пульса в минуты без шагов** (утверждено). Нужно хотя бы 60 таких минут,
  иначе `null`;
- `peak_hr` — максимум из поминутных медиан пульса, чтобы одиночные выбросы не давали пик. Допущение;
- `wear_minutes` и `status` (см. F6).

**Дневная сводка:** значения дня D и разница с днём D−1 (абсолютная и в %). Если одной из сторон нет,
показывается «нет данных для сравнения».

**Недельная сводка** (ISO-неделя, пн–вс по локальным датам) и разница с предыдущей неделей. Для каждой метрики
своя база усреднения:

| Метрика | По каким дням считается среднее |
|---|---|
| Шаги в день, активные минуты | Дни со статусом `complete` |
| **Сон** | **Валидные ночи** (`night_valid = true`), независимо от статуса дня |
| Пульс в покое | Дни, где `resting_hr` посчитан (не `null`) |
| Пиковый пульс | Максимум по дням, где `peak_hr` не `null` |

Рядом с каждой метрикой показывается, по скольким дням она посчитана: «шаги: 5 из 7 дней», «сон: 6 из 7 ночей».
Если база пустая, выводится «нет данных». Дни `partial` видны на графике, но в средние шагов и активности не входят.

#### F8. Цели
- Два типа: `steps` (шагов в день, по умолчанию 8000) и `sleep` (часов сна, по умолчанию 8). Значения
  по умолчанию — допущение.
- Цели хранятся с историей (`valid_from`). Прогресс за прошлые дни считается по цели, действовавшей в тот день.
- Прогресс: для дня — значение и процент от цели (прогресс-бар); для недели — «цель выполнена N из 7 дней».
- **Уведомление о достижении цели:** при пересчёте сводки, как только значение за дату перешло порог и
  записи в `goal_achievements` ещё нет, создаётся запись, уведомление в колокольчике и **сразу** отправляется
  SSE-событие `goal.achieved`. Во всех открытых вкладках появляется тост.
  - Допущение: тост показывается только для сегодняшней и вчерашней даты (по `Clock`). Достижения за прошлые
    даты из исторического импорта попадают в ленту уведомлений без тостов, чтобы не было лавины.
  - Для цели по сну днём считается день пробуждения.

#### F9. Правила и рекомендации
Правила утверждены заказчиком. Пороги заданы в коде и в `rules.params` (JSONB), пользователь их не редактирует.

| Код | Условие срабатывания | Условие автозакрытия | Нужные данные |
|---|---|---|---|
| **R1** Недосып | 3 валидные ночи подряд, в каждой сна < 6 ч | Есть валидная ночь со сном ≥ 7 ч | 3 валидные ночи подряд |
| **R2** Мало шагов | 3 полных дня подряд, шагов < 50% цели | Полный день с выполненной целью по шагам | 3 полных дня подряд |
| **R3** Повышенный пульс в покое | 2 дня подряд пульс в покое ≥ базы + 7 уд/мин. База — среднее за 14 дней до этих двух, нужно ≥ 7 значений | Последний день с посчитанным пульсом в покое: < базы + 4 (гистерезис, допущение) | Посчитанный пульс в покое за нужные дни |
| **R4** Сон хуже, чем на прошлой неделе | Средний сон за прошлую ISO-неделю меньше, чем за позапрошлую, на ≥ 60 мин | Разница < 30 мин | В каждой неделе ≥ 5 валидных ночей |
| **R5** Нерегулярный отбой | Стандартное отклонение времени отбоя за последние 7 ночей > 90 мин | < 60 мин | ≥ 5 валидных ночей из 7 |
| **R6** Нет активности | 5 полных дней подряд, активных минут < 15 | Полный день с ≥ 15 активными минутами | 5 полных дней подряд |

- Для R5 время отбоя считается по кругу суток: 23:30 и 00:30 отличаются на 60 минут, а не на 23 часа.
- **Опорная дата оценки.** Допущение: для R2, R3 и R6 это вчера по поясу пользователя (сегодняшний день
  не закончен). Для R1 и R5 — сегодня, если сегодняшняя ночь валидна, иначе вчера. Для R4 — последняя
  завершённая ISO-неделя. «Сегодня» берётся из `Clock`.
- **Когда оцениваются правила:** после завершения задачи загрузки, после каждой потоковой пачки (с дебаунсом
  в 10 с), при включении правила, при смене часового пояса и раз в час по таймеру воркера (на случай смены суток).
- **Машина состояний** для пары (пользователь, правило):
  - условие истинно и открытой рекомендации нет → создаётся `recommendation(status=open)` со снимком значений
    (`context`) → уведомление в интерфейсе, событие `recommendation.opened`, запись в `email_outbox`;
  - условие истинно и рекомендация уже открыта → **ничего не происходит**. Повторов нет, пока ситуация
    не изменилась;
  - выполнено условие закрытия и рекомендация открыта → `status=resolved`, `resolve_reason='auto'`, событие
    `recommendation.resolved`. Отдельное письмо о закрытии не отправляется (допущение);
  - данных недостаточно → ничего не меняется.
  - Защита на уровне БД: частичный уникальный индекс `UNIQUE(user_id, rule_code) WHERE status='open'`.
- **Отключение правила:** правило перестаёт оцениваться. Допущение: открытая рекомендация по нему закрывается
  со статусом `closed_rule_disabled`. **История сохраняется** и видна с фильтром по правилу. При повторном
  включении правило оценивается заново.
- **Отзыв:** у любой рекомендации (открытой или закрытой) можно поставить «полезно» или «не полезно»,
  поменять или снять отметку. Отметка хранится с меткой времени.
- Описание правил для пользователя — на странице «Правила» и в `docs/RULES.md`.

#### F10. Письма (дайджест)
- SMTP-отправка в **Mailpit** (docker-compose, веб-интерфейс на `http://localhost:8025`).
- Каждая новая открытая рекомендация попадает в `email_outbox` со статусом `pending`.
- **Планировщик отправки** — чистая функция
  `plan_send_time(pending, last_digest_local_date, tz_history, quiet_hours, now) → datetime`
  с исчерпывающими unit-тестами. Время отправки дайджеста с ожидающими записями считается так:
  1. **Окно и потолок:** `T = min(последнее добавление + WINDOW, первое ожидающее добавление + MAX_DELAY)`,
     где `DIGEST_WINDOW_MINUTES = 15` и `DIGEST_MAX_DELAY_MINUTES = 60` (оба задаются через env).
     Каждая новая рекомендация сдвигает отправку на 15 минут, но **не дальше чем на 60 минут после первой**.
  2. **Не больше одного дайджеста в сутки** по местному времени пользователя (пояс из истории на момент `T`).
     Если за эти локальные сутки дайджест уже отправлен, `T` переносится на 00:00 следующих локальных суток.
     Всё накопившееся уходит следующим письмом.
  3. **Тихие часы** (начало и конец в локальном времени, могут переходить через полночь, например 22:00–08:00):
     если `T` попадает в тихие часы, `T` переносится на их окончание.
     Допущение (утверждено пользователем, ADR-017): если начало тихих часов равно концу, тихие часы считаются
     выключенными.
  4. После шага 3 шаг 2 проверяется ещё раз: дата могла смениться.
  - **Приоритет:** лимит «одно письмо в сутки» и тихие часы сильнее потолка в 60 минут. Потолок защищает
    только от бесконечного сдвига окна.
- Диспетчер в воркере (тик раз в 30 с) отправляет пользователю **одно письмо со всеми ожидающими
  рекомендациями**, когда `Clock.now() ≥ T`.
- Допущение: в письмо попадают только рекомендации, которые на момент отправки ещё открыты. Записи
  рекомендаций, закрытых до отправки, помечаются `skipped`. Если открытых не осталось, письмо не отправляется
  и суточный лимит не расходуется.
- Защита от повторов: `email_digests` хранит `local_date`, на него стоит частичный уникальный индекс
  `UNIQUE(user_id, local_date) WHERE sent_at IS NOT NULL`. Запись в outbox привязывается к дайджесту в той же
  транзакции. Повторный тик ничего не отправляет второй раз.
- В `email_digests` сохраняются `planned_at` и причина переноса (`window`, `max_delay`, `daily_limit`,
  `quiet_hours`). Это видно на dev-панели и помогает отладке.
- Письмо уходит на почту из настроек. Тема: «Трекер здоровья: N новых рекомендаций». Тело — текст и HTML
  со списком и ссылкой на приложение.
- Допущение: если пользователь не указал почту, письма не отправляются, а в интерфейсе показывается предупреждение.

#### F11. Настройки
- **Страница «Настройки»:** почта для писем; часовой пояс (выбор из IANA, поле «действует с», по умолчанию
  «сейчас»), список истории поясов; тихие часы (вкл/выкл, начало, конец).
- Допущение (утверждено пользователем, ADR-017): «действует с» в будущем (позже `Clock.now()`) запрещено → 422.
  Переезд можно указать только сейчас или в прошлом.
- После смены пояса пересчитываются затронутые дни и правила, всем вкладкам уходит событие `settings.changed`.

#### F12. Реальное время и две вкладки
- **SSE:** `GET /api/events`, авторизация по cookie. Воркер и API публикуют события через Postgres
  `NOTIFY` в канал `user_events`. Каждый процесс API делает `LISTEN` и раздаёт события открытым
  SSE-соединениям нужного пользователя.
- События: `ingest.progress`, `ingest.done`, `summary.updated {dates}`, `goal.achieved`, `recommendation.opened`,
  `recommendation.resolved`, `recommendation.feedback`, `rule.toggled`, `settings.changed`, `goal.changed`,
  `notification.created`, `digest.sent`. Полезная нагрузка маленькая: идентификаторы и даты, не больше 8 КБ
  из-за лимита NOTIFY.
- Фронтенд по событию инвалидирует нужные ключи TanStack Query. При обрыве соединения EventSource
  переподключается и делает полный refetch.
- Итог: **любое изменение в одной вкладке появляется во второй не позже чем через 2 секунды**.

#### F13. Генератор тестовых данных
CLI на Python в папке `generator/`, запуск `uv run htgen …`. Возможности:
- `--start`, `--end` или `--days` — произвольный период;
- `--devices watch,phone`:
  - часы: шаги поминутно, пульс с шагом `--hr-interval` (по умолчанию 5 с), сон;
  - телефон: шаги интервалами по 5 минут, сон менее точный (±20 мин), пульса нет;
  - в часы прогулок данные пишут **оба** устройства, телефон насчитывает примерно 90–97% шагов часов.
    Так проверяется, что шаги не суммируются;
  - `--unaligned`: границы интервалов не совпадают с началом минуты (например, `08:00:30`). Нужен для проверки,
    что соседние интервалы не теряют шаги;
- `--tz Europe/Moscow` и `--tz-change "2026-10-05T12:00Z=America/New_York"` — смещения в метках времени меняются;
- пропуски: `--gap "2026-10-03T00:00/2026-10-04T12:00@watch"` (явные) и `--gap-prob 0.05 --gap-max-hours 30`
  (случайные). В пропуске устройство не пишет **ничего**;
- `--scenario` — заготовки для демо правил: `short-sleep` (R1), `sedentary` (R2, R6), `high-rhr` (R3),
  `irregular` (R5), `worse-week` (R4), `recovery` (исправление ситуации, чтобы проверить автозакрытие);
- `--seed` — детерминированный результат;
- `--out file.ndjson` — запись в файл. `--stream --url http://localhost:8000 --batch-size 1000 --rate 5` — отправка
  пачек в API. Для авторизации логинится с `--email` и `--password`, по умолчанию берёт демо-пользователя из env;
- повторный запуск с тем же seed на частично пересекающийся период выдаёт те же записи в пересечении.
  Это нужно для проверки дедупликации.
- Генератор никогда не создаёт пересекающиеся интервалы шагов одного устройства.

## 4. Нефункциональные требования

**Производительность**
- Файл ~200 МБ (≈3 млн записей: 90 дней, два устройства, пульс каждые 5 с) обрабатывается на обычном ноутбуке
  за ≤ 5 минут. Допущение: ориентир, реальная цифра фиксируется в `STATUS.md`.
- Память воркера не растёт с размером файла: парсинг потоковый, пачки фиксированного размера.
- Пока идёт загрузка, интерфейс отзывчив: никаких долгих синхронных запросов, все страницы открываются.
- Сводки берутся из предрассчитанной таблицы `daily_summaries`. p95 ответа API для дашборда < 300 мс
  на локальной машине.
- Минутные таблицы пересчитываются только для затронутых диапазонов, а не целиком.
- Индексы: первичные ключи исходных таблиц, GiST-индекс exclusion constraint, `(device_id, minute_utc)` на
  минутных таблицах, `(user_id, local_date)` на сводках.

**Надёжность и корректность**
- Идемпотентность всех операций загрузки, пересчётов и отправки писем.
- Изменения состояния и постановка задач в очередь — в одной транзакции (очередь в той же БД).
- Перезапуск воркера не теряет задачи: при `locked_at` старше 5 минут задача возвращается в очередь.
- Производные данные можно полностью пересобрать из исходных командой `htadmin rebuild --user <email>`.
  Тест: пересборка даёт тот же результат.

**Безопасность**
- argon2id для паролей; httpOnly-cookie сессии; CSRF-заголовок; `SameSite=Lax`.
- Все запросы к данным отфильтрованы по `user_id` текущей сессии. Есть тест, что чужие данные недоступны (404).
- Валидация входных данных через Pydantic, лимиты на размер файла и пачки.
- Секреты только в `.env`, в репозитории `.env.example`.
- Ошибки не раскрывают стектрейсы клиенту (в prod-режиме).
- Dev-эндпоинты (`/api/dev/*`) недоступны при `APP_ENV != dev`. Есть тест на это.

**Адаптивность и UI**
- Интерфейс на русском.
- Вёрстка не ломается от 375 px (телефон) до десктопа. Допущение: отдельная мобильная вёрстка не нужна,
  но без горизонтального скролла и наездов элементов.
- Светлая тема. Допущение: тёмная тема не обязательна.
- Состояния загрузки и пустые состояния есть везде (скелетоны, «данных пока нет — загрузите файл»).

**Развёртывание и кроссплатформенность**
- `docker compose up --build` поднимает всё: postgres, api, worker, frontend, mailpit. Миграции и сид
  применяются автоматически при старте api.
- Предварительные требования: Docker Desktop (Windows, macOS) или Docker Engine с Compose v2 (Linux), Git.
  Для разработки без Docker: Python 3.12 и `uv`, Node.js 22 LTS.
- Скрипты есть и для Windows, и для Unix: `scripts/*.ps1` и `scripts/*.sh`. Допущение: Makefile не используем,
  у заказчика Windows.
- **`.gitattributes` в корне** (этап 0), чтобы на Windows скрипты и файлы для контейнеров не получали CRLF
  и не падали в Linux-контейнерах:
  ```gitattributes
  * text=auto
  *.sh text eol=lf
  Dockerfile text eol=lf
  *.conf text eol=lf
  *.ps1 text eol=crlf
  ```
  Допущение: правила для `Dockerfile`, `*.conf` и `*.ps1` добавлены сверх запрошенного `*.sh`.

**Наблюдаемость**
- Структурированные логи в JSON (`structlog`) с `job_id` и `user_id`.
- `GET /api/health` — проверка БД и последнего тика воркера.

## 6. Архитектура и структура проекта

### 6.1. Компоненты
```
[Browser: React SPA] ──HTTP /api/*──► [nginx (frontend)] ──proxy──► [API: FastAPI]
        ▲                                                            │   ▲
        └──────────── SSE /api/events ◄──────────────────────────────┘   │ LISTEN user_events
                                                                         │
[generator --stream] ──HTTP /api/ingest/batch──► [API] ──INSERT job──► [PostgreSQL] ◄──► [Worker]
                                                                                           │
                                                                              SMTP ──► [Mailpit :8025]
```
- **API** — HTTP, авторизация, чтение сводок, постановка задач, SSE.
- **Worker** — отдельный процесс (`python -m app.worker`). Выполняет задачи `ingest_file`, `ingest_batch`,
  `recompute` (минуты → сводки → цели), `evaluate_rules`, `tz_changed`, а также периодические тики:
  диспетчер писем (30 с) и оценку правил (1 ч). Последовательность по одному пользователю обеспечивает
  advisory lock.
- **Конвейер обработки:** исходные записи → минутные таблицы устройства → объединение по минутам →
  `daily_summaries` → цели → правила → outbox → дайджест.
- **Frontend** — в dev-режиме Vite dev server с proxy `/api` → api:8000; в compose — сборка и nginx с proxy.
  Один origin, поэтому нет CORS и cookie работают. Для SSE в nginx `proxy_buffering off`.

### 7.2. Формат входных данных (NDJSON, `docs/DATA_FORMAT.md`)
Одна JSON-запись на строку. Метки времени в ISO 8601 **обязательно со смещением**, допускаются секунды.
```json
{"type":"meta","schema":"ht.v1","generator":"htgen 0.1","devices":[{"id":"watch-1","kind":"watch","name":"Часы"},{"id":"phone-1","kind":"phone","name":"Телефон"}]}
{"type":"steps","device":"watch-1","start":"2026-10-01T08:00:30+03:00","end":"2026-10-01T08:01:30+03:00","count":112}
{"type":"steps","device":"phone-1","start":"2026-10-01T08:00:00+03:00","end":"2026-10-01T08:05:00+03:00","count":530}
{"type":"sleep","device":"watch-1","start":"2026-09-30T23:41:00+03:00","end":"2026-10-01T07:12:00+03:00"}
{"type":"hr","device":"watch-1","ts":"2026-10-01T08:00:05+03:00","bpm":96}
```
- Строка `meta` необязательна. Неизвестное устройство без meta создаётся с типом `phone` и предупреждением
  в отчёте. Допущение.
- В потоковом режиме (`/api/ingest/batch`) используется тот же формат записей в JSON-массиве. Устройства
  передаются полем `devices` в теле.
- Валидация: `end > start`, `count ≥ 0`, `30 ≤ bpm ≤ 230`, интервал не длиннее 24 ч. Строки, которые
  не прошли проверку, получают класс `invalid`.

**Этап 2. Формат данных и генератор (файловый режим)**
- `docs/DATA_FORMAT.md`. CLI `htgen`: период, устройства, `--unaligned`, пояс и смена пояса, пропуски, сценарии, seed.
- Тесты: детерминизм по seed; в пропусках нет записей; у часов и телефона пересекаются прогулки; интервалы

**Этап 3. Приём данных**
- Исходные таблицы (с `btree_gist` и exclusion constraint), `devices`, `ingest_jobs`, `jobs`. Очередь и воркер.
- Загрузка файла (stream to disk) → задача → потоковый парсер → staging → классификация
  new/duplicate/conflict/invalid → вставка → прогресс и checkpoint. Отчёт загрузки.
- Пересчёт минутных таблиц (`steps_minute`, `sleep_minute`, `coverage_minute`) для затронутых диапазонов.
- Тесты:
  - повторная загрузка того же файла: 0 `new`, всё `duplicate`, производные данные не изменились;
  - частично пересекающийся файл: `new` только для непересекающейся части;
  - тот же ключ с другим `count` → `conflict`, сохранено первое значение;
  - пересекающийся интервал одного устройства с другими границами → `conflict`;
  - **соседние невыровненные интервалы** `08:00:30–08:01:30` и `08:01:30–08:02:30` → минута 08:01 = сумма вкладов,
    ничего не потеряно;
  - property-тест (hypothesis): для любого набора непересекающихся интервалов сумма `steps_minute` по устройству
    равна сумме `count` в `steps_raw` (с точностью до округления);
  - рестарт воркера посреди файла → итог тот же;
  - `htadmin rebuild` даёт тот же результат.

**Этап 4. Объединение, дни, сводки**
- `localtime.py` (история поясов), `merge.py` (часы важнее телефона, возвращает значение и `source_device_id`),
  `metrics.py` (сессии сна, день пробуждения, валидность ночи, пульс в покое по 10-му перцентилю, пик по
  поминутной медиане, время ношения и статус дня), `weekly.py` (базы усреднения по F7).
- Пересчёт «грязных» дат во время загрузки.
- Тесты (основная доказательная база):
  - **инвариант объединения (property-тест):** для каждой минуты объединённое значение равно значению ровно одного
    устройства (часов, если минута покрыта часами, иначе телефона) и никогда не равно сумме, если оба устройства
    дали ненулевые значения;
  - прогулка, записанная обоими устройствами (часы 2000, телефон 1900) → 2000;
  - день: прогулка 1 только на телефоне (часы сняты, 3000) и прогулка 2 на обоих (часы 2000, телефон 1900) →
    **5000**, то есть больше, чем у любого устройства по отдельности (часы 2000, телефон 4900). Это корректно;
  - сон 23:40–07:10 относится к дню пробуждения;
  - переезд MSK→NYC и обратно: сумма шагов за период равна сумме по объединённым минутам, ни одна минута не потеряна
    и не посчитана дважды;
  - пропуск → `no_data`, а не 0; меньше 12 ч ношения → `partial`;
  - **недельный сон:** ночь записана целиком (`night_valid`), а день `partial` → ночь входит в средний сон недели;
    шаги этого дня в среднее шагов не входят.

**Этап 5. Реальное время и загрузка в UI**
- NOTIFY/LISTEN, `/api/events`, `useEvents` (инвалидация).
- Страница «Загрузка» с двумя прогресс-барами и историей (счётчики new, duplicate, conflict, invalid).
- Проверка (ADR-015): интеграционные тесты SSE (два клиента одного пользователя получают события ≤ 2 с, чужой
  пользователь не получает) и smoke первого байта SSE через nginx. Ручная проверка пользователем остаётся:
  в двух вкладках прогресс виден в обеих.

**Этап 6. Дашборд**
- День и неделя, сравнение с прошлым периодом, подписи баз усреднения, графики с пропусками, страница устройств.
- Проверка (ADR-015): тест «сводки есть до завершения задачи» (пауза воркера после пачки k), тест дашборда
  «перезапрос по `summary.updated`», e2e №2. Ручная проверка пользователем остаётся: сводка заполняется
  в процессе обработки большого файла.

**Этап 7. Цели**
- Модель с историей, страница целей, прогресс, `goal_achievements`, уведомления и тост, колокольчик.
- Тесты: достижение цели при поступлении данных создаёт одно уведомление; повторная загрузка не создаёт второе;
  тост только для сегодня и вчера по `Clock`.

**Этап 8. Правила и рекомендации**
- Сид правил R1–R6 с описаниями (перенесён с этапа 1, ADR-016).
- Движок, R1–R6 (каждое правило в своём модуле с unit-тестами: срабатывание, повтор без дубля, автозакрытие,
  недостаточно данных → без изменений), страница правил (вкл/выкл), страница рекомендаций, отзывы.
- `docs/RULES.md`.
- Тесты: отключённое правило не срабатывает, история сохраняется; включение заново оценивает правило;
  R1 срабатывает на валидных ночах даже в дни `partial`.

**Этап 9. Письма**
- Outbox, `planner.plan_send_time`, диспетчер, Mailpit, `docs/EMAIL.md`, очередь дайджестов на dev-панели.
- Unit-тесты планировщика (с фиксированным `Clock`):
  - 3 рекомендации в пределах 15 минут → 1 письмо через 15 минут после последней;
  - рекомендации каждые 10 минут → письмо ровно через 60 минут после первой (потолок);
  - после отправки сегодняшнего дайджеста пришла новая рекомендация → письмо **завтра**, а не сегодня;
  - перенос на завтра упирается в тихие часы 22:00–08:00 → отправка в 08:00 завтрашнего дня;
  - рекомендация в тихие часы → отправка в момент их окончания;
  - смена пояса: лимит «одно письмо в сутки» считается по местной дате на момент отправки;
  - рекомендация закрыта до отправки → не попадает в письмо; если открытых не осталось, письма нет;
  - повторный тик диспетчера не отправляет второй раз.
- Интеграционный тест: письмо реально появляется в Mailpit (через API Mailpit).

**Этап 10. Настройки**
- Почта, тихие часы, часовой пояс с «действует с», пересчёт затронутых дней и правил, событие `settings.changed`,
  ближайший запланированный дайджест.

**Этап 11. Потоковый режим**
- `/api/ingest/batch`, `htgen --stream`. Дашборд обновляется в реальном времени.
- Тест: поток и затем файл с теми же данными → всё `duplicate`, без изменений итогов.

**Этап 12. E2E-тесты (Playwright).** Каждый сценарий работает на своём свежем пользователе. Время двигается через
`/api/dev/clock`, в e2e-окружении `DIGEST_WINDOW_MINUTES=1`. Обязательные сценарии:
1. Регистрация, вход, выход.
2. Загрузка файла: прогресс-бар меняется, страница отзывчива (во время обработки можно перейти на другую
   страницу), сводка появляется до окончания обработки.
3. Повторная загрузка того же файла: итоги не изменились, в отчёте 0 `new`.
4. **Две вкладки** (два `page` в одном контексте): загрузка, отключение правила и отметка «полезно» в первой
   видны во второй ≤ 2 с.
5. День с пропуском отображается как «нет данных».
6. Сценарий `short-sleep` → рекомендация R1 в UI → письмо-дайджест в Mailpit → загрузка `recovery` →
   рекомендация закрыта.
7. Тихие часы: письмо не пришло в тихие часы и пришло после их окончания.
8. **Лимит дайджестов:** после первого письма за сутки срабатывает ещё одно правило → письма нет;
   сдвиг `Clock` на следующие сутки → приходит второе письмо. За одни локальные сутки в Mailpit не больше одного
   письма на пользователя.
9. Цель достигнута → тост.
10. Отключённое правило не срабатывает, история видна.
- Скрипт `scripts/test.ps1`/`.sh` запускает всё: unit, integration, e2e.

**Этап 13. Документация и сдача**
- `README.md`: описание; чем делали (модель и инструмент, почему — **заполняет пользователь, агент оставляет
  место и напоминает**); предварительные требования; запуск за 3 команды; демо-сценарий; тесты; ссылки на docs;
  использованные шаблоны и генераторы (Vite template, shadcn/ui CLI).
- `docs/STATUS.md` — честная таблица «требование → статус (работает / частично / нет) → чем доказано
  (тест, скриншот)», известные проблемы, замеры производительности.
- `docs/NEXT.md` — что сделали бы следующим заходом.
- `scripts/demo.ps1`/`.sh`: поднять compose, сгенерировать файл, загрузить, открыть дашборд и Mailpit.
- `scripts/bench_ingest.ps1`/`.sh`: генерирует ~200 МБ, загружает, замеряет время и пиковую память воркера,
  пишет результат в `docs/STATUS.md` (заменяет ручной замер из §9 #6, ADR-015).
- `scripts/fresh_clone_check.ps1`/`.sh`: чистый клон во временную папку → `.env` из `.env.example` →
  `docker compose up --build` → smoke → вход демо-пользователя (проверка §9 #1 и #21 на Windows, ADR-015).
- `scripts/check_docs.py` (stdlib): обязательные разделы README, в STATUS.md все критерии 1–23 со статусом
  «работает / частично / нет» и доказательством, относительные ссылки в docs открываются, NEXT.md не пуст.
  Допущение (утверждено пользователем, ADR-017).
- Скриншоты в `docs/screenshots/`.
- Финальная запись в WORKLOG с временем окончания и общей длительностью. Напоминание пользователю приложить
  экспорт сессии.

## 9. Критерии готовности

| # | Требование | Как проверить |
|---|---|---|
| 1 | Запуск одной командой | Чистый клон (в том числе на Windows) → `cp .env.example .env` → `docker compose up --build` → `http://localhost:5173` открывается, демо-вход работает |
| 2 | Приём сна, шагов, пульса | Загрузка файла `htgen` → в отчёте записи всех трёх типов, сводка заполнена |
| 3 | Генератор: период и пропуски | `htgen --days 90 --gap-prob 0.05` → unit-тесты генератора зелёные, пропуски видны на дашборде |
| 4 | Несколько устройств, без суммы шагов | **Проверка по минутам:** property-тест, что значение каждой объединённой минуты взято ровно с одного устройства (часы, если покрыта часами, иначе телефон) и никогда не является суммой. Плюс сценарий «прогулка 1 только телефон (3000), прогулка 2 оба (2000/1900)» → день = 5000. Дневной итог **может** превышать итог любого устройства по отдельности, это не ошибка |
| 5 | Ничего не теряется на невыровненных интервалах | Тест соседних интервалов `08:00:30–08:01:30` + `08:01:30–08:02:30`; property-тест «сумма минут = сумма исходных» |
| 6 | Большой файл не блокирует UI | e2e №2; `scripts/bench_ingest.ps1` на файле ~200 МБ пишет время и пиковую память воркера в STATUS.md (ADR-015). Ручная проверка пользователем остаётся |
| 7 | Сводка обновляется по мере обработки | e2e №2: данные появляются до `ingest.done` |
| 8 | Повторная или пересекающаяся загрузка без дублей | Интеграционные тесты классификации (new/duplicate/conflict) и e2e №3 |
| 9 | Пропуск = нет данных; правила на пропусках не срабатывают | Unit-тесты метрик и правил, e2e №5 |
| 10 | Дневная и недельная сводки со сравнением | Тест API `summary/day` и `summary/week`; тест, что средний сон считается по валидным ночам, а шаги по полным дням |
| 11 | Цели и прогресс; уведомление сразу | Тест `goal_achievements`, e2e №9 |
| 12 | Правила R1–R6, видны, отключаются | Unit-тесты на каждое правило, e2e №10 |
| 13 | Нет ежедневного повтора, автозакрытие | Unit-тесты машины состояний, e2e №6 |
| 14 | Рекомендации за день — в одном письме | Unit-тесты планировщика (окно, потолок 60 мин, лимит 1/сутки, перенос на следующий день) и e2e №8: не больше одного письма за локальные сутки |
| 15 | Тихие часы откладывают письма | Unit-тесты планировщика (через полночь, вместе с лимитом), e2e №7 |
| 16 | История рекомендаций с отзывом | e2e (отметка «полезно» сохраняется, видна во 2-й вкладке) |
| 17 | Сон в правильный день | Unit-тест «вечер → утро» |
| 18 | Смена пояса: без потерь и удвоений | Unit-тест переезда (сумма до = сумма после) |
| 19 | Две вкладки | e2e №4 |
| 20 | Изоляция пользователей, dev-эндпоинты закрыты в prod | Интеграционные тесты (чужие данные → 404; `/api/dev/*` при `APP_ENV=prod` → 404). Допущение (утверждено, ADR-017): плюс сквозной тест по всем маршрутам из OpenAPI — чужой ресурс → 404, изменяющий запрос без CSRF-заголовка → 403, dev-маршрут в prod → 404 |
| 21 | Скрипты работают после клона на Windows | `.gitattributes` есть; `git ls-files --eol` показывает LF для `*.sh`; `scripts/fresh_clone_check.ps1` на Windows → exit 0 (контейнеры стартуют, smoke и демо-вход проходят; ADR-015) |
| 22 | Процесс прозрачен | ≥ 1 коммит на фичу; WORKLOG с реальными метками на каждый этап и фичу; DECISIONS заполнен; PROMPTS лежит; `CLAUDE.md` в корне; CI зелёный |
| 23 | Честный статус | `STATUS.md` и `NEXT.md` заполнены, нерабочее помечено как нерабочее |

Этап считается готовым, только если тесты зелёные, коммиты сделаны, а WORKLOG обновлён.

## 10. Что НЕ входит в проект
- Реальные интеграции с устройствами и платформами (Apple Health, Google Fit, Garmin), Bluetooth.
- Любые LLM и ML: рекомендации строятся только по правилам.
- Нативное мобильное или десктопное приложение, PWA, push-уведомления.
- Восстановление пароля, подтверждение email, OAuth и SSO, 2FA, роли и админка.
- Настоящая отправка почты: только Mailpit.
- Редактирование порогов правил и пользовательские правила; ручной разбор конфликтов загрузки.
- Стадии сна, SpO2, калории, HRV, ЭКГ и другие метрики.
- Медицинская интерпретация. Рекомендации носят информационный характер, в интерфейсе есть дисклеймер.
- Продовое развёртывание (HTTPS, домен, бэкапы, масштабирование), нагрузочное тестирование.
- Мультиязычность: только русский интерфейс.
- Тёмная тема и отдельная мобильная вёрстка (только «не ломается на 375 px»).
- Экспорт и удаление данных пользователем.
